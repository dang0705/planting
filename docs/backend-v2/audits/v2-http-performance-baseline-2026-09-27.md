# v2 公开植物读取：首轮 HTTPS 时延基线

## 测量范围

- 时间：2026-09-27；环境：CloudBase v2 测试环境 `cloud1-2grufevs395a9d5e`。
- 对象：已部署的 `GET /api/v2/plant-knowledge/plants/pid_cbtest_monstera_001`；25 次串行请求均返回 HTTP 200。
- 客户端：本机 `curl`，记录 `time_connect`、`time_starttransfer` 和 `time_total`。以下统计使用完整响应的 `time_total`，包括客户端到网关的网络时间、云函数运行和响应传输。
- 本次未重启函数，也未先做专门预热；第 1 次请求耗时 1200.994 毫秒，其余 24 次介于 184.576 至 300.875 毫秒。不能仅凭该差异断言冷启动。

按最近秩计算，25 次样本的 p50 为 **244.940 毫秒**，p95 为 **300.875 毫秒**，p99 为 **1200.994 毫秒**。配置目录中的非 AI API p95/p99 目标分别为 800/1500 毫秒；本样本数、单一路径和单一客户端不足以证明目标已达成，更不能代表高并发、不同地区或登录用户植物读取。

CloudBase 日志服务已启用。以 `logType:accesslog AND path:"/api/v2/plant-knowledge/plants/pid_cbtest_monstera_001"` 只读检索 2026-09-27 11:02—11:04（北京时间）的网关访问日志，得到 25 条 HTTP 200；按日志 `timeCost` 统计，p50 **74 毫秒**、p95 **134 毫秒**、最高 **1002 毫秒**。日志的起止时间差也证实 `timeCost` 的单位为毫秒。条数与请求时段吻合，但本机测量未保存网关请求编号，不能逐条严格配对。网关 `timeCost` 不是 MySQL 或云函数分段耗时；两组数值的差也不能直接称为“网络耗时”。

同一时段以 `function_name:"v2-plant-knowledge" AND status_code:"200" AND log:"Report RequestId"` 读回 25 条函数报告：执行 `duration` 的 p50 **15 毫秒**、p95 **68 毫秒**、最高 **73 毫秒**。首次调用附近另有 1 条 `Init Report`，记录 `Coldstart: 377ms`（其中运行时初始化 9ms、函数初始化 368ms）；因此本轮可以确认出现过冷启动，但不能把首个网关 1002 毫秒全部归因于它。日志与客户端数据只按时间窗和数量关联，未作请求编号逐一配对。

同日 `v2-user-plant` 网关日志中只有两条成功的单株 GET 样本，`timeCost` 分别为 **945** 和 **97 毫秒**；样本过少且缺少建连、身份查询、业务查询的内部计时，不据此计算可靠分位数或决定连接池参数。

## 可行动结论

- 在同一测试库对已验收的公开植物读取 SQL 执行只读 `EXPLAIN FORMAT=JSON`：估算成本为 `1.00`，6 个访问点均为 `const`、各估算 1 行，命中植物公开引用、分类主键、当前发布指针及发布明细的唯一索引，未见全表扫描。该成本是优化器估算，**不是毫秒耗时**；不能据此解释上述 HTTP 时延。
- 已认证用户植物读取的会话、用户和植物索引均存在；但以合成参数执行的 `EXPLAIN` 返回 `no matching row in const table`，未得到可用的完整连接顺序。不能把它当成真实用户植物查询已验证的性能结论，也不为补计划读取真实用户会话。
- CloudBase MySQL 管理端在该环境对 `qinghuazhi_v2_test` 只读执行 `SELECT @@max_connections AS max_connections, @@wait_timeout AS wait_timeout_seconds`，读回分别为 `1000` 和 `3600`；请求 ID 为 `f499f533-68a1-46b3-ba0f-1fcab240e018`。这是当前实例配置值，不是青花植可以独占的连接额度，也不能推导云函数最大实例数。
- 当前代码路径的公开植物读取每请求新建一条 MySQL 连接并执行一条 SELECT。已认证用户植物 GET 先用一条独立连接读取会话，再新建另一条连接，为单株 SELECT 执行 `BEGIN` 与 `COMMIT`；`release` 会关闭连接而非复用。源码路径计数不是运行时分段计时，也不能单凭往返次数断定它们在总延迟中的占比。
- 公开植物读取的函数执行阶段已有系统报告，暖请求的函数耗时较小；当前证据不支持优先为该路径改索引或连接池。用户植物读取仍缺可靠样本和内部阶段划分；下一次性能切片应先增加**脱敏的分段计时**，至少区分建连、身份查询、业务查询及完整 HTTP 请求，再与 CloudBase 真实连接容量一同决定是否连接复用。
- 虽已读回数据库当前总连接上限，云函数最大实例数、其他业务占用与并发峰值仍未确认；不据此配置连接池大小或预置并发。不得把首请求较慢直接归因为 SQL 或冷启动。

本轮只执行公开读请求、只读日志和数据库配置核对；未修改云端函数、网关、数据库或用户数据。
