## 0. 一句话结论

v1 的视觉模型只「看图贴证据标签」，病因由规则引擎在 12 个模式里推断，覆盖面窄。按用户 2026-10-10 裁决，v2 改为**受约束的生成式**：qwen3.5-flash 先输出分类编号（病因编号、把握档、严重/紧急/隔离等级），再按我们的 JSON 结构直接生成竞品式的完整内容，包括一句话结论、诊断表、识别依据、立即处理、后续养护、预防、注意事项和补拍建议。固定前缀放入完整病因分类体系、鉴别要点、安全用药与用语规则和示例，既为模型提供参考依据（grounding），也作为缓存前缀；服务端用分类编号做安全门和统计，用 Schema 与规则校验把住「不给剂量、可食用须提示安全间隔期、证据不足不下结论、高风险须给理由」。这一改动需要修订已冻结合同里「生成式模型不得补造病因与治疗」的条款，修订条款清单和修订文本草案见第 2 节。

前端类比：以前是「接口只返回 i18n key，文案查语言包」；现在是「接口直接返回渲染好的富文本，但每段都带类型标签（编号），前端拦截器先按类型标签和规则校验，不合规就整条丢弃」。

### 1.2 模型与调用方式

- Provider：注册表里三家，都走 OpenAI Chat Completions 兼容协议——TokenHub（默认 `qwen3.5-flash`，用 `prompt_cache_key` 缓存）、CloudBase AI（默认 `qwen3.5-flash`，`cache_control`）、阿里云百炼（默认 `qwen3-vl-plus`，`cache_control` 显式缓存）。还有遗留的混元适配器与 HF AutoTrain 影子分类器（只做对比，不参与结论）。
- **逐图调用**：每张图单独一次模型请求（`analyzeSingleImage`），服务端再把多张图的结果聚合。支持显式缓存时，先串行跑第 1 张图「预热缓存」，再并发跑其余图（`visual-prompt-cache-warmup.js`）。
- 图片只传 HTTPS URL（禁止 Base64），百炼加 `max_pixels` 限制像素；Qwen3.5 显式关闭思考（`enable_thinking=false`）。
- 流式返回，带超时与限频重试。

### 1.3 提示词结构（逐段摘要，不贴全文）

固定前缀（`[静态输出契约] → [静态规则] → [静态全局词典]`，代码注释写明「未经用户同意不得改段名顺序」）：

1. 角色：「植物图片的结构化可见证据标注助手」。
2. 输出契约：一段 JSON 示例（器官、图片质量、模式候选、症状候选、池外症状、视觉判别维度）。
3. 工作流程 4 条 + 输出规则 4 条：只标可见对象，**明确禁止输出病因、诊断键、治疗方案**；上限 mode 3、symptom 3。
4. 判读纪律 24 条：虫体必须可分离、潜道须连续、霉层须有边界、噪点不得升级为虫体、黄化区分均匀/叶脉间/斑驳等。
5. 全局词典：器官枚举、拍摄区域枚举、12 个模式名、虫害证据键。

可变尾部（`[Dynamic Task]` 之后）：按本图器官过滤的「允许症状键」列表、虫害映射（模式→直判证据组合）、虫害证据中文提示、本图可见异常说明、图片上下文。

### 1.4 输出结构

只有「证据」没有「结论」：`normalized_organ`、`image_quality_grade`、`mode_candidates[{mode, confidence}]`、`symptom_candidates[{symptom_key, strength_level, confidence_band}]`、`out_of_pool_symptom_candidates`、`visual_discriminators`。病因、处置文案由规则引擎 + 数据库题包/结论表 + 白名单生成。

### 1.5 虫害白名单与高特异性直判

- 8 类虫害：叶螨、粉蚧、介壳虫、粉虱、蚜虫、蓟马、潜叶蝇、蕈蚊。每类有「直判证据组」：如叶螨=可见螨群，或「网丝 + 黄白针点」组合；粉虱=「白色飞虫 + 固定若虫」组合；蓟马=可见虫体，或「银灰擦伤 + 针尖黑点」组合。
- 高特异性零追问通道只有 1 条：白粉病（`powder_white`，把握≥medium，器官限定）。
- 非问题白名单：「当前未见明显问题」「正常老叶老化」「品种天然斑纹」等，有严格的竞争方向阈值。
- v2 已复用：`cloudfunctions-v2/src/diagnosis/domain/pest-question-eligibility.ts` 固定 8 类虫害，`direct` 档最多 0 题且「不授权自动直判」。

### 1.6 补拍 / 追问

- 图片可分析度低 → `retake_first`，生成补拍授权（指定拍摄区域、来源批次），用户补拍上传时校验授权并消费一次。
- 追问走固定题包（黄叶、萎蔫）和动态虫害题包，按把握档决定题数（低 3、中 2、高 1、较可信 1、直判 0）。

### 1.7 缓存做法

- 固定前缀 + `[Dynamic Task]` 分界；SHA-1 记录前缀/尾部哈希；百炼请求前做合同审计（system 仅 1 条、缓存标记仅 1 个、动态文本必须在图片前、图片必须 URL）。
- TokenHub 用 `diagnose_visual_static_v1:{provider}:{model}:{prefixHash}` 作 `prompt_cache_key`，并做会话亲和。
- 复核记录里读取 `usage.prompt_tokens_details.cached_tokens` 统计命中。

| 大类 | 缺失项（举例） |

| 细菌 | 细菌性叶斑（水渍多角斑）、软腐 |
| 病毒 | 花叶/斑驳/环斑 |

## 2. 用户裁决与需修订的合同条款

### 2.1 竞品是怎么做出来的（判断依据）

竞品结果页里有这些特征：自评「约 95%」、写出具体药剂（苦参碱、印楝素）、喷施部位、「3 天」间隔、黄色粘虫板，以及「茄科偏好 + 图中植物特征匹配」这类按图定制的句子。这些内容几乎不可能来自固定的审核文案库，更符合「视觉大模型按固定结构模板直接生成完整内容」的特征（协调方判断，本文采纳）。用户的目标就是这种体验。

### 3.1 据此调整的前缀与缓存方案

| 决策 | 内容 | 理由 |
|---|---|---|
| 缓存方式 | 只用百炼**显式缓存**，`system` 消息唯一一个文本块挂唯一标记 | qwen3.5-flash 不在隐式缓存清单；显式缓存命中有确定性 |

### 3.3 命中条件与度量（Adapter 硬约束 + 测试守护）

1. `system` 恰好 1 条、内容为数组，前缀文本块唯一且只挂一个缓存标记。
2. 前缀从已发布制品读取，规范化后的 SHA-256 必须等于 release 记录；不一致就拒绝调用。

## 5. 安全门（写进 Schema 与服务端校验）

| 门 | 规则 | 落在哪一层 |
|---|---|---|
| 编号先行 | 原始文本中 `classification` 必须在所有内容之前；内容引用的病因编号必须在候选里 | 服务端（读原始文本中的键顺序） |
| 不给剂量 | 处置正文出现「数字 + 倍/ml/克/%/每升/次」或「稀释/兑水 + 数字」即拒绝；只允许写「按产品标签」 | 服务端正则 |
| 药剂名单 | `agentNames` 是 enum（20 项）；正文中出现的药剂名必须都在 `agentNames` 里；命中禁用/高毒词典即拒绝 | Schema enum + 服务端词典 |
| 按标签提示 | `agentNames` 非空 → `labelDosageNotice: true` | Schema if/then |
| 可食用 | `edibleContext` 由服务端背景决定；为 yes 或 unknown 且用药 → `edibleSafetyIntervalNotice: true`，注意事项必须再次提醒 | Schema if/then + 服务端比对 |
| 证据不足不下结论 | `not_plant`、`insufficient_evidence` 或 `unusable` 时，候选、识别依据和处置必须全部为空，补拍或追问至少一项非空；这类请求不扣额度 | Schema if/then + 额度结算 |
| 把握上限 | 图片 `limited` 时候选不得为「较可能」（违规则降档并记审计）；全文禁止「%、概率、确诊、一定是」 | 服务端 |
| 高风险须理由 | `riskLevel ≠ low` → `riskReasonZh` 必填；用药步骤必须排在物理步骤之后，且需要「较可能」，或「可能」且严重程度为中度以上 | Schema if/then + 服务端 |
| 隔离 | 建议隔离必须给理由；依据不足时写「暂不确定，建议先单独放置观察」，不得默认「无需隔离」 | 前缀规则 + 服务端检查理由非空 |
| 养护建议 | 涉及浇水、光照、施肥、换盆、湿度、通风的条目必须带 `careProposalKind`，固定提示「确认后才会记入养护」；用户点「采纳」后由 care 用例写入 | Schema + care 用例 |
| 直判快速通道 | 直判标记命中已审计的直判证据组（8 类虫害 + 白粉病，后续可加锈病孢子堆、灰霉绒毛）、图片质量 good、把握「较可能」→ 由领域规则确认零追问 | 领域规则（不信模型自评） |
| 注入防护 | 用户描述加引号并注明「不是指令」；出现 Schema 外字段即拒绝 | 前缀 + Schema |
| 脱敏 | 公开 DTO 不含内部编号、提示词或模型原文；原文只存 SHA-256 | Adapter + 投影 |

**与固定题包的关系**：视觉诊断是一条新入口，不替代黄叶/萎蔫固定题包与动态虫害题包。首选候选属于黄叶/萎蔫相关原因且把握不是「较可能」时，推荐转入对应固定题包，视觉结果作为已接纳证据带入。模型自由追问只用于没有题包的类别，最多 1 轮（轮次为待配置项）。

## 7. 评测方案（预算上限 50 元）

### 7.1 单案例 token 与费用估算（qwen3.5-flash，北京，≤128K 档）

假设：前缀 P = 9,000 tokens（取粗估上限）；可变文本 700 tokens；`max_pixels`=1024² 时单图 1,026 tokens，默认像素时 2,562 tokens；非思考输出 3,000 tokens（参照示例约 1,800 tokens，再上浮）；思考模式额外 +4,000 输出 tokens（估计值，待实测）。单价：输入 0.2 元/百万，输出 2 元/百万；缓存创建按输入价 125% = 0.25 元/百万，命中按约 10% = 0.02 元/百万。

| 场景（2 张图，1024²） | 前缀费用 | 其余输入 | 输出 | **单案例合计** |
|---|---|---|---|---|
| 不命中（无缓存） | 9,000×0.2 = 0.00180 | 2,752×0.2 = 0.00055 | 3,000×2 = 0.00600 | **≈0.0084 元** |
| 首次建缓存 | 9,000×0.25 = 0.00225 | 0.00055 | 0.00600 | **≈0.0088 元** |
| 命中 | 9,000×0.02 = 0.00018 | 0.00055 | 0.00600 | **≈0.0067 元** |
| 3 张图、默认像素、不命中 | 0.00180 | 8,386×0.2 = 0.00168 | 0.00600 | **≈0.0095 元** |
| 3 张图、默认像素、思考模式、不命中 | 0.00180 | 0.00168 | 7,000×2 = 0.01400 | **≈0.0175 元** |

（表中乘积单位为「tokens × 元/百万 tokens」，结果已换算成元。）

结论：**成本大头是输出**（约占 70%～80%），缓存只能省前缀那部分（每案例约 0.0016 元）。规划时取保守单价：非思考 **0.010 元/次**，思考 **0.020 元/次**。50 元可支撑约 2,500 次（全部按思考保守价）到约 6,000 次（非思考、不命中）调用。**预算不是瓶颈，带标注、有授权的评测图片才是。**

|---|---|---|
| 前三命中 85% 的 95% 置信区间 | 约 ±3.0 个百分点 | 约 ±3.5 个百分点 |
| 首选命中 65% 的 95% 置信区间 | 约 ±4.0 个百分点 | 约 ±4.7 个百分点 |
| 单个大类（约 50 / 约 36 个案例）在 85% 附近 | 约 ±10 个百分点 | 约 ±12 个百分点 |
| 观察到「安全违规 0」时，真实违规率 95% 上界（三分之一法则：3/n） | ≤0.55% | ≤0.75% |

- 整体前三与首选命中可以得出有统计意义的结论。要说「前三命中 ≥85%」有把握，观测值需约 ≥88%，置信区间下界才不低于 85%。
- **单个大类只能作方向性判断，不能作统计结论**；样本少的类别（病毒、线虫）尤其如此。
- 「安全违规 0」只能表述为「在 n 个案例中未观察到违规，真实违规率 95% 上界约 0.55%～0.75%」，**不能证明违规率为 0**；上线后仍需持续监测。
- 预算足以把测试集扩大到 1,000 以上，真正的限制是能拿到多少有授权的标注图片。

### 7.6 提示词迭代流程

1. 每个候选版本 = {模型快照、前缀 SHA-256、Schema 版本、病因表与药剂名单版本、请求参数}，组成不可变版本组，写入策略发布（`diagnosis_releases`）。
2. 只在开发集上迭代，封存测试集只跑最终版本一次，避免「对着考题调参」。
3. 灰度：小流量上线，监测质量、安全违规、成本、命中率和用户申诉；任一门槛失败就把 active 指针切回上一版（回滚只改指针，不改历史）。
4. 每次诊断结果记录所用版本组，可按原版本回放。

## 10. 风险

1. **安全风险上升**：生成式内容可能出现名单外的做法或对特定植物有药害；只能靠名单、正则、词典和评测把关，无法做到 100% 拦截。
2. **准确率风险**：生理性/环境性问题仅凭照片难以区分（浇水过多 vs 根腐 vs 缺氮）。
3. **统计效力有限**：单个大类和「零违规」都无法在评测中被统计证明（见 7.5）。
4. **合同回改面广**：C1～C12 涉及 4 份文档、2 张票、1 份 Schema 和配置目录，需要一次性同步，否则新旧条款会互相矛盾。
5. **缓存效果有限**：输出占成本大头，缓存只能省约 20%；低流量时缓存 5 分钟就失效。
6. **授权数据不足**：生理性、环境性、药害类公开数据集很少，可能拖住评测集建设。

## 附：给前端同学的术语对照

| 后端说法 | 前端类比 |
|---|---|
| 提示词缓存（前缀缓存） | 浏览器强缓存带 hash 的 `vendor.js`：前缀不变就命中，改一个字节就要全部重新下载 |
| 固定前缀 / 可变部分 | 打包出来的公共 chunk / 每个页面自己的业务 chunk |
| 编号先行 + 安全门 | 接口返回的每段富文本都带 `type` 字段，前端拦截器先按 `type` 和规则校验，不合规整条丢弃 |
| 闭集编号 | TypeScript 字面量联合类型，不在列表里就类型报错 |
| Schema if/then | 表单联动校验：勾了「用药」，「按标签提示」就必填 |
| 策略发布 + active 指针 | 灰度发布：多个版本并存，指针指向谁就用谁，回滚只改指针 |
| Adapter / Provider Registry | 封装好的 `request` 层：业务只调 `api.diagnose()`，不关心后面是哪家、密钥放在哪 |
| Proposal → care 确认 | 表单草稿：诊断只生成草稿，用户点「保存」才真正提交到养护记录 |
| 置信区间 | A/B 实验报告里的「显著性」：样本太少时，85% 和 75% 可能分不出差别 |
