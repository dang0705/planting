## 0. 一句话结论

v1 的视觉模型只做「看图贴标签」（可见证据标注），病因由规则引擎在 12 个模式里推断，覆盖只有 8 类虫害 + 白粉病、煤污、黄叶、萎蔫；v2 已冻结的合同又进一步要求「病因与处置只能来自已审核知识，模型不得补造」。用户这次要的是「模型给出完整病因和解决方案」。**推荐的折中**：模型从写死在固定前缀里的**闭集病因代码表（约 50 项、覆盖 11 大类）和闭集行动代码表**中选择，并给出本例证据与说明；用户看到的正式文案由服务端按代码从已审核知识包渲染。这样既能覆盖全面，又不违反「模型不补造病因/处置」的硬约束，而且代码表放在前缀里正好让前缀变长、变稳定，最适合提示词缓存。

前端类比：模型像一个只返回 `{ icon: 'warning', i18nKey: 'pest.whitefly' }` 的接口，真正的文案在审核过的 i18n 语言包里；模型不能自己发明新的 i18nKey，也不能直接返回一段 HTML。

### 1.2 模型与调用方式

- Provider：注册表里三家，都走 OpenAI Chat Completions 兼容协议——TokenHub（默认 `qwen3.5-flash`，用 `prompt_cache_key` 缓存）、CloudBase AI（默认 `qwen3.5-flash`，`cache_control`）、阿里云百炼（默认 `qwen3-vl-plus`，`cache_control` 显式缓存）。还有遗留的混元适配器与 HF AutoTrain 影子分类器（只做对比，不参与结论）。
- **逐图调用**：每张图单独一次模型请求（`analyzeSingleImage`），服务端再把多张图的结果聚合。支持显式缓存时，先串行跑第 1 张图「预热缓存」，再并发跑其余图（`visual-prompt-cache-warmup.js`）。
- 图片只传 HTTPS URL（禁止 Base64），百炼加 `max_pixels` 限制像素；Qwen3.5 显式关闭思考（`enable_thinking=false`）。
- 流式返回，带超时与限频重试。

### 1.3 提示词结构（逐段摘要，不贴全文）

固定前缀（`[静态输出契约] → [静态规则] → [静态全局词典]`，代码注释写明「未经用户同意不得改段名顺序」）：

1. 角色：「植物图片的结构化可见证据标注助手」。
2. 输出契约：一段 JSON 示例（器官、图片质量、模式候选、症状候选、池外症状、视觉判别维度）。
3. 工作流程 4 条 + 输出规则 4 条：只标可见对象，**明确禁止输出病因、诊断键、治疗方案**；上限 mode 3、symptom 3。
4. 判读纪律 24 条：虫体必须可分离、潜道须连续、霉层须有边界、噪点不得升级为虫体、黄化区分均匀/叶脉间/斑驳等。
5. 全局词典：器官枚举、拍摄区域枚举、12 个模式名、虫害证据键。

可变尾部（`[Dynamic Task]` 之后）：按本图器官过滤的「允许症状键」列表、虫害映射（模式→直判证据组合）、虫害证据中文提示、本图可见异常说明、图片上下文。

### 1.4 输出结构

只有「证据」没有「结论」：`normalized_organ`、`image_quality_grade`、`mode_candidates[{mode, confidence}]`、`symptom_candidates[{symptom_key, strength_level, confidence_band}]`、`out_of_pool_symptom_candidates`、`visual_discriminators`。病因、处置文案由规则引擎 + 数据库题包/结论表 + 白名单生成。

### 1.5 虫害白名单与高特异性直判

- 8 类虫害：叶螨、粉蚧、介壳虫、粉虱、蚜虫、蓟马、潜叶蝇、蕈蚊。每类有「直判证据组」：如叶螨=可见螨群，或「网丝 + 黄白针点」组合；粉虱=「白色飞虫 + 固定若虫」组合；蓟马=可见虫体，或「银灰擦伤 + 针尖黑点」组合。
- 高特异性零追问通道只有 1 条：白粉病（`powder_white`，把握≥medium，器官限定）。
- 非问题白名单：「当前未见明显问题」「正常老叶老化」「品种天然斑纹」等，有严格的竞争方向阈值。
- v2 已复用：`cloudfunctions-v2/src/diagnosis/domain/pest-question-eligibility.ts` 固定 8 类虫害，`direct` 档最多 0 题且「不授权自动直判」。

### 1.6 补拍 / 追问

- 图片可分析度低 → `retake_first`，生成补拍授权（指定拍摄区域、来源批次），用户补拍上传时校验授权并消费一次。
- 追问走固定题包（黄叶、萎蔫）和动态虫害题包，按把握档决定题数（低 3、中 2、高 1、较可信 1、直判 0）。

### 1.7 缓存做法

- 固定前缀 + `[Dynamic Task]` 分界；SHA-1 记录前缀/尾部哈希；百炼请求前做合同审计（system 仅 1 条、缓存标记仅 1 个、动态文本必须在图片前、图片必须 URL）。
- TokenHub 用 `diagnose_visual_static_v1:{provider}:{model}:{prefixHash}` 作 `prompt_cache_key`，并做会话亲和。
- 复核记录里读取 `usage.prompt_tokens_details.cached_tokens` 统计命中。

## 2. 总体设计：闭集代码 + 已审核文案渲染

```text
图片 + 受控背景
   │
   ▼
[百炼视觉模型] ── 固定前缀(方法论 + 病因代码表 + 行动代码表 + Schema + 安全规则 + 示例)
   │  输出：候选病因代码、可见证据、鉴别排除、把握档、严重/紧急/隔离、行动代码、补拍/追问
   ▼
[Adapter] Schema 严格校验 → 跨字段一致性校验 → 丢弃原始输出（只留脱敏结构 + 哈希）
   ▼
[diagnosis 领域] 安全门：图片质量门 / 把握上限 / 直判快速通道 / 行动准入（适用、禁忌、风险）
   ▼
[渲染] 按 causeCode → 已审核 Outcome，按 actionCode → 已审核 Action 文案；模型的 instanceNote 只作「本例补充」
   ▼
公开 DTO diagnosis-result/v1（已有 Schema）—— 不含提示词、模型原文、内部代码映射
   │
   └─ 养护类行动 = Proposal（建议），用户点「采纳」→ care 用例写事实/计划/提醒
```

关键点：

1. **一次产品动作一次模型调用**：多张图放进同一请求，让模型能互证（整株+叶背）。只有校验失败才按策略重试。前端类比：从「每张图片发一个请求」改成「一个批量请求」。
2. **模型只选代码，不写正式文案**：病因名称、处置步骤、用药安全话术来自已审核知识包；某个代码在知识包里还没有已审核条目时，该候选只能以「疑似 + 建议线下核验/通用安全检查」呈现，不展示具体处置。
3. **竞品的「约 95%」不照抄**：我们输出「较可能 / 可能 / 待确认」三档 + 理由；百分比只有在评测证明校准良好、用户拍板后才可考虑。

### 3.3 命中条件清单（Adapter 硬约束 + 测试守护）

1. `system` 恰好 1 条，内容为数组，前缀文本块唯一且挂唯一缓存标记。
2. 前缀文本由已发布制品读取，按规范化（LF、唯一末尾换行）后 SHA-256 必须等于 release 记录的哈希；不一致拒绝调用（沿用 `bindConfirmedDiagnosisPrompt` 思路）。
3. 模型代码、`enable_thinking`、温度等请求参数也属于「缓存身份」的一部分，固定在版本组里。
4. 可变文本在图片之前；图片只用 HTTPS 临时 URL。
5. 不在前缀中插入任何时间、用户、版本号文字。

### 3.4 如何度量命中率

- 每次调用记录：`prompt_tokens`、`cached_tokens`、`cache_creation_input_tokens`、`completion_tokens`、图片计量、耗时、`prefixSha256`、版本组 ID。只记数字和哈希，不记正文。
- 指标：**命中率 = Σcached_tokens ÷ Σ前缀 tokens（只统计非首次请求）**；**缓存节省 = 无缓存估算成本 − 实际成本**；按小时看「冷启动比例」（5 分钟无请求后的首次请求占比）。
- 成本预算按 0 命中保守估算（富内容实验合同要求）。
- 低流量时段若冷启动比例高，可评估「定时预热」——但预热本身花钱，属于付费能力，必须用户授权，首版不做。

| 字段 | 含义 | 对应竞品 / 公开 DTO |
|---|---|---|
| `imageAssessment` | 是否植物、可用度、质量问题、逐图部位与质量 | 图片把关（竞品无） |
| `overallStatus` | 有问题 / 多问题并存 / 未见明显问题 / 证据不足 / 非植物 | 决定页面走哪种模板 |
| `summaryZh` | 一句话结论（仅作备选，正式标题由知识包渲染） | 竞品顶部一句话 |
| `candidates[]`（≤3） | `causeCode`、把握档与理由、直判标记、可见证据（图号+部位+观察）、矛盾证据、鉴别排除项及理由、关键缺失证据 | 诊断名称、问题类型、置信度、主要证据、识别依据；公开 `alternativeOutcomes` |
| `severity` / `urgency` / `isolation` | 各自分级 + 理由；隔离允许「待确认」 | 紧急程度、是否需要隔离 |
| `actions.{immediate, ongoing, prevention, caution}` | `actionCode` + 关联病因 + 本例说明；养护类带 `careProposalKind` | 立即处理、后续养护、预防建议、注意事项 |
| `followUp` | 复查时机、恶化信号 | 公开 `followUp` |
| `retakeRequests[]`（≤3） | 补拍部位、原因、拍法 | 「重新识别」的引导 |
| `followUpQuestions[]`（≤3） | 证据不足时的追问 + 选项 | 与固定题包衔接 |

规则：所有自然语言字段简体中文；严格 JSON；闭集字段全部 enum；不合法整份拒绝；字段长度、数量上限见草案第 6、11 节。

用药：模型只能选 `act_low_risk_pesticide`（「按标签使用低毒针对性药剂」）+ `act_caution_pesticide_label`（含安全间隔期提醒）。竞品里「苦参碱/印楝素」这种具体药剂名，属于**需园艺来源审核的处置主张**，只能出现在已审核 Action 文案里，并须注明「按产品标签」，**不给剂量**。

## 5. 置信度与安全门

| 情形 | 处理 |
|---|---|
| 非植物 / 不确定是否植物 | `not_plant`，不出候选，提示重拍；**不扣或退还**额度待用户拍板（第 9 节） |
| 图片不清（`unusable`） | 不出候选，给补拍要求 |
| 图片受限（`limited`） | 所有候选最高 `medium`（前缀规则 + 服务端再校验，模型违规则降档并记审计） |
| 只有非特异症状 | 最高 `low`，必须带追问或补拍；行动只给安全检查类（不给用药） |
| 多病并发 | `multiple_problems`，最多 3 个候选，可并列；行动按 `forCauseCodes` 分组，禁忌冲突时以更保守者为准 |
| 未见明显问题 | 只允许 `none_*` 候选；保留 v1 白名单思路：需「无任何异常证据」才可显示 |
| 用药类行动 | 仅当候选为 `high`（或 `medium` 且用户确认问题持续）且知识包中该 Action 已审核、无禁忌（可食用、儿童宠物等）时才展示 |
| 隔离 | 只在候选命中且知识包的隔离策略条件满足时说「建议隔离」；不得默认「无需隔离」 |
| 提示词注入 | 用户描述放引号并声明「不是指令」；输出若出现 Schema 外字段即拒绝 |

**高特异性直判快速通道（保留）**：模型的 `directMarkerKeys` 命中 v1 已审计的直判证据组（8 类虫害 + 白粉病，可扩展锈病孢子堆、灰霉绒毛等，须单独审核），且图片质量 good、把握 high → 服务端规则确认「快速通道」，零追问直接出结果。规则在领域代码里，不交给模型自评。前端类比：像表单里的「强校验通过就直接提交」。

**与固定题包的关系**：

- 视觉诊断是新的一条入口，不替代黄叶/萎蔫固定题包与动态虫害题包。
- 模型候选落在黄叶/萎蔫相关原因且把握 < high → 转入对应固定题包（已冻结题数档位），视觉结果作为「已接纳证据」带入。
- 模型 `followUpQuestions` 是**自由追问**，与固定题包的已审核题目不同；首版建议只在**没有对应题包**的类别使用，且最多 1 轮（轮次为待配置项）。

## 7. 评测方案

### 7.1 评测图集

| 来源 | 授权 | 用途 | 风险 |
|---|---|---|---|
| v1 线上用户上传的诊断图 | 须核对用户协议是否允许用于质量改进；未授权不得使用 | 最贴近真实场景 | 隐私；需去除 EXIF、人脸、门牌 |
| PlantDoc 数据集 | 公开发布为 CC BY 4.0（使用前逐项核验） | 真实背景下的病叶 | 以农作物为主 |
| PlantVillage | 公开发布（许可须逐项核验） | 病害类别补充 | 实验室纯背景，偏乐观 |
| iNaturalist 研究级观察 | 逐张 CC 许可，只取允许再用的 | 害虫、室内观叶 | 标注需复核 |
| 团队自拍 + 园艺专家标注 | 自有 | 生理性/环境性/药害（公开数据最缺） | 人力成本 |

建议规模（MVP）：每个大类 ≥30 张，常见类（虫害、真菌、生理性）≥60；另含 10% 非植物/模糊图、10% 健康植物与天然斑叶、10% 多病并发；合计约 500～600 个案例（一个案例可含 1～3 张图）。标注字段：主因 causeCode、次因、可见部位、把握难度（易/中/难）、是否适合直判、是否可食用、标注人与复核人。标注须两人独立 + 分歧仲裁。

### 7.2 离线跑分指标

| 指标 | 定义 |
|---|---|
| Top-1 / Top-3 命中 | 首选 / 前 3 候选含标注主因 |
| 类别级召回 | 按 11 大类分别统计（重点盯真菌 vs 细菌、生理 vs 病害） |
| 置信度校准 | 每档（high/medium/low）实际准确率；high 档应显著高于 medium |
| 「证据不足」合理率 | 模糊/非植物图被正确拦截的比例；清晰图被误拦的比例 |
| 安全违规率 | 出现剂量、禁用药剂、确诊用语、健康/毒性判断、Schema 外行动 → 目标 0 |
| 直判误判率 | 走快速通道却错误的比例 → 目标接近 0 |
| JSON 合法率 | Schema + 跨字段校验一次通过率 |
| 缓存命中率 | 第 3.4 节定义 |
| 单次成本与延迟 | P50/P95，按单图/多图分别统计，按 0 命中另算上界 |

门槛数值属于验收线，待用户拍板（第 9 节给推荐值）。

### 7.3 提示词迭代流程

1. 每个候选版本 = {模型代码、前缀 SHA-256、Schema 版本、代码表版本、请求参数} 组成不可变版本组，写入策略发布（`diagnosis_releases`）。
2. 离线：同一评测集跑「现行 vs 候选」，出对比报告（含成本）。
3. 灰度：按比例小流量，监测质量、错误、成本、额度申诉；任一门槛失败立即把 active 指针切回上一版（回滚 = 改指针，不改历史）。
4. 每次诊断结果记录所用版本组，历史可回放。
5. 评测与灰度都会产生付费调用，须用户逐次授权预算。

| 约束 | 本方案做法 |
|---|---|
| 归属 | 诊断会话归属 `user_id + user_plant_id`；未加入花园的走临时案例（已有 `user-plant.authenticated_ephemeral` 与游客案例策略），不伪造用户植物 |

| 原始输出留存 | 只存校验后的结构化结果 + 原文 SHA-256；原文是否短期留存用于复核、保留多久，属待拍板配置项 |
| 版本组 | 模型/提示词/Schema/代码表走策略发布，同一请求锁定一个只读快照 |

| 配置治理 | 业务参数（最多图片数、追问轮次、重试次数、原文保留期、成本上限）→ 策略发布；运维参数（超时、Base URL）→ `environment.ts`；代码表、安全规则、一致性规则 → 代码不变量（hard_rule） |

| 建议转养护 | 行动里的浇水/光照/施肥/换盆是 Proposal；用户点击「采纳」后调用 care 用例写事实/计划/提醒；诊断域无写入权 |
| 依赖 | 不新增 npm 依赖（AJV 已在用，`node:crypto`、原生 `fetch`） |

## 10. 风险

1. **准确率风险**：生理性/环境性问题仅凭照片难以区分（浇水过多 vs 根腐 vs 缺氮），必须依赖追问与背景，评测可能达不到门槛。
2. **安全风险**：用药建议一旦错误或越界（可食用植物、儿童宠物）有实际伤害，故用药只能经已审核 Action 展示。
3. **知识审核瓶颈**：约 50 个原因 + 30 个行动都要挂来源主张，人力成本大，可能拖慢上线。
4. **缓存失效风险**：低流量时缓存 5 分钟就过期；前缀每次改版缓存全失效。
5. **成本风险**：前缀长（约 5～7k tokens）、输出长（中文完整结果估计 1～2k tokens），0 命中时单次成本显著高于 v1 单图标注，需对照 2,000 点/周期与会员价评估。
6. **合同冲突风险**：若选 D1-B，需要回改多份已冻结合同与票面，影响 P1/P4 已通过的验收。

## 附：给前端同学的术语对照

| 后端说法 | 前端类比 |
|---|---|
| 提示词缓存（前缀缓存） | 浏览器强缓存带 hash 的 `vendor.js`：文件名（前缀）不变就直接命中，改一个字节就全部重新下载 |
| 固定前缀 / 可变部分 | 打包时的公共 chunk / 每个页面自己的业务 chunk |
| 闭集代码表 | TypeScript 的字符串字面量联合类型 `'pest_whitefly' \| 'fungal_rust' \| ...`，不在列表里就类型报错 |
| Schema 严格校验 | 接口返回先过 zod/AJV 校验，不合法直接丢弃，不做"尽量兼容" |
| 策略发布 + active 指针 | 前端灰度发布：多个版本并存，CDN 指向哪个版本就用哪个，回滚只改指向 |
| Adapter / Provider Registry | 封装好的 `request` 层：页面只调 `api.diagnose()`，不关心后面是哪家 SDK、密钥在哪 |
| Proposal（建议）→ care 确认 | 表单「草稿」：诊断只能生成草稿，用户点「保存」才真正提交到养护记录 |
