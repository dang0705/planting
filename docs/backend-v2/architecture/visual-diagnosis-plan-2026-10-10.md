## 0. 一句话结论

v1 的视觉模型只「看图贴证据标签」，病因由规则引擎在 12 个模式里推断，覆盖面窄。按用户 2026-10-10 裁决，v2 改为**受约束的生成式**：qwen3.5-flash 先输出分类编号（病因编号、把握档、严重/紧急/隔离等级），再按我们的 JSON 结构直接生成竞品式的完整内容，包括一句话结论、诊断表、识别依据、立即处理、后续养护、预防、注意事项和补拍建议。固定前缀放入完整病因分类体系、鉴别要点、安全用药与用语规则和示例，既为模型提供参考依据（grounding），也作为缓存前缀；服务端用分类编号做安全门和统计，用 Schema 与规则校验把住「不给剂量、可食用须提示安全间隔期、证据不足不下结论、高风险须给理由」。这一改动需要修订已冻结合同里「生成式模型不得补造病因与治疗」的条款，修订条款清单和修订文本草案见第 2 节。

前端类比：以前是「接口只返回 i18n key，文案查语言包」；现在是「接口直接返回渲染好的富文本，但每段都带类型标签（编号），前端拦截器先按类型标签和规则校验，不合规就整条丢弃」。

### 1.2 模型与调用方式

- Provider：注册表里三家，都走 OpenAI Chat Completions 兼容协议——TokenHub（默认 `qwen3.5-flash`，用 `prompt_cache_key` 缓存）、CloudBase AI（默认 `qwen3.5-flash`，`cache_control`）、阿里云百炼（默认 `qwen3-vl-plus`，`cache_control` 显式缓存）。还有遗留的混元适配器与 HF AutoTrain 影子分类器（只做对比，不参与结论）。
- **逐图调用**：每张图单独一次模型请求（`analyzeSingleImage`），服务端再把多张图的结果聚合。支持显式缓存时，先串行跑第 1 张图「预热缓存」，再并发跑其余图（`visual-prompt-cache-warmup.js`）。
- 图片只传 HTTPS URL（禁止 Base64），百炼加 `max_pixels` 限制像素；Qwen3.5 显式关闭思考（`enable_thinking=false`）。
- 流式返回，带超时与限频重试。

### 1.3 提示词结构（逐段摘要，不贴全文）

固定前缀（`[静态输出契约] → [静态规则] → [静态全局词典]`，代码注释写明「未经用户同意不得改段名顺序」）：

1. 角色：「植物图片的结构化可见证据标注助手」。
2. 输出契约：一段 JSON 示例（器官、图片质量、模式候选、症状候选、池外症状、视觉判别维度）。
3. 工作流程 4 条 + 输出规则 4 条：只标可见对象，**明确禁止输出病因、诊断键、治疗方案**；上限 mode 3、symptom 3。
4. 判读纪律 24 条：虫体必须可分离、潜道须连续、霉层须有边界、噪点不得升级为虫体、黄化区分均匀/叶脉间/斑驳等。
5. 全局词典：器官枚举、拍摄区域枚举、12 个模式名、虫害证据键。

可变尾部（`[Dynamic Task]` 之后）：按本图器官过滤的「允许症状键」列表、虫害映射（模式→直判证据组合）、虫害证据中文提示、本图可见异常说明、图片上下文。

### 1.4 输出结构

只有「证据」没有「结论」：`normalized_organ`、`image_quality_grade`、`mode_candidates[{mode, confidence}]`、`symptom_candidates[{symptom_key, strength_level, confidence_band}]`、`out_of_pool_symptom_candidates`、`visual_discriminators`。病因、处置文案由规则引擎 + 数据库题包/结论表 + 白名单生成。

### 1.5 虫害白名单与高特异性直判

- 8 类虫害：叶螨、粉蚧、介壳虫、粉虱、蚜虫、蓟马、潜叶蝇、蕈蚊。每类有「直判证据组」：如叶螨=可见螨群，或「网丝 + 黄白针点」组合；粉虱=「白色飞虫 + 固定若虫」组合；蓟马=可见虫体，或「银灰擦伤 + 针尖黑点」组合。
- 高特异性零追问通道只有 1 条：白粉病（`powder_white`，把握≥medium，器官限定）。
- 非问题白名单：「当前未见明显问题」「正常老叶老化」「品种天然斑纹」等，有严格的竞争方向阈值。
- v2 已复用：`cloudfunctions-v2/src/diagnosis/domain/pest-question-eligibility.ts` 固定 8 类虫害，`direct` 档最多 0 题且「不授权自动直判」。

### 1.6 补拍 / 追问

- 图片可分析度低 → `retake_first`，生成补拍授权（指定拍摄区域、来源批次），用户补拍上传时校验授权并消费一次。
- 追问走固定题包（黄叶、萎蔫）和动态虫害题包，按把握档决定题数（低 3、中 2、高 1、较可信 1、直判 0）。

### 1.7 缓存做法

- 固定前缀 + `[Dynamic Task]` 分界；SHA-1 记录前缀/尾部哈希；百炼请求前做合同审计（system 仅 1 条、缓存标记仅 1 个、动态文本必须在图片前、图片必须 URL）。
- TokenHub 用 `diagnose_visual_static_v1:{provider}:{model}:{prefixHash}` 作 `prompt_cache_key`，并做会话亲和。
- 复核记录里读取 `usage.prompt_tokens_details.cached_tokens` 统计命中。

### 3.1 据此调整的前缀与缓存方案

| 决策 | 内容 | 理由 |
|---|---|---|
| 缓存方式 | 只用百炼**显式缓存**，`system` 消息唯一一个文本块挂唯一标记 | qwen3.5-flash 不在隐式缓存清单；显式缓存命中有确定性 |

### 3.3 命中条件与度量（Adapter 硬约束 + 测试守护）

## 5. 安全门（写进 Schema 与服务端校验）

> **r4 分期说明**：首版只启用本表中的**安全门**。「直判快速通道」与第 13 节的规则仲裁属于中长期规则层，首版不启用（见第 14 节）。

| 门 | 规则 | 落在哪一层 |
|---|---|---|
| 编号先行 | 原始文本中 `classification` 必须在所有内容之前；内容引用的病因编号必须在候选里 | 服务端（读原始文本中的键顺序） |
| 不给剂量 | 处置正文出现「数字 + 倍/ml/克/%/每升/次」或「稀释/兑水 + 数字」即拒绝；只允许写「按产品标签」 | 服务端正则 |
| 药剂名单 | `agentNames` 是 enum（20 项）；正文中出现的药剂名必须都在 `agentNames` 里；命中禁用/高毒词典即拒绝 | Schema enum + 服务端词典 |
| 按标签提示 | `agentNames` 非空 → `labelDosageNotice: true` | Schema if/then |
| 可食用 | `edibleContext` 由服务端背景决定；为 yes 或 unknown 且用药 → `edibleSafetyIntervalNotice: true`，注意事项必须再次提醒 | Schema if/then + 服务端比对 |
| 证据不足不下结论 | `not_plant`、`insufficient_evidence` 或 `unusable` 时，候选、识别依据和处置必须全部为空，补拍或追问至少一项非空；这类请求不扣额度 | Schema if/then + 额度结算 |
| 把握上限 | 图片 `limited` 时候选不得为「较可能」（违规则降档并记审计）；全文禁止「%、概率、确诊、一定是」 | 服务端 |
| 高风险须理由 | `riskLevel ≠ low` → `riskReasonZh` 必填；用药步骤必须排在物理步骤之后，且需要「较可能」，或「可能」且严重程度为中度以上 | Schema if/then + 服务端 |
| 隔离 | 建议隔离必须给理由；依据不足时写「暂不确定，建议先单独放置观察」，不得默认「无需隔离」 | 前缀规则 + 服务端检查理由非空 |
| 养护建议 | 涉及浇水、光照、施肥、换盆、湿度、通风的条目必须带 `careProposalKind`，固定提示「确认后才会记入养护」；用户点「采纳」后由 care 用例写入 | Schema + care 用例 |
| 直判快速通道 | 直判标记命中已审计的直判证据组（8 类虫害 + 白粉病，后续可加锈病孢子堆、灰霉绒毛）、图片质量 good、把握「较可能」→ 由领域规则确认零追问 | 领域规则（不信模型自评） |
| 注入防护 | 用户描述加引号并注明「不是指令」；出现 Schema 外字段即拒绝 | 前缀 + Schema |
| 脱敏 | 公开 DTO 不含内部编号、提示词或模型原文；原文只存 SHA-256 | Adapter + 投影 |

**与固定题包的关系**：视觉诊断是一条新入口，不替代黄叶/萎蔫固定题包与动态虫害题包。首选候选属于黄叶/萎蔫相关原因且把握不是「较可能」时，推荐转入对应固定题包，视觉结果作为已接纳证据带入。模型自由追问只用于没有题包的类别，最多 1 轮（轮次为待配置项）。

## 7. 评测方案（预算上限 50 元）

### 7.1 单案例 token 与费用估算（qwen3.5-flash，北京，≤128K 档）

假设：前缀 P = 9,000 tokens（取粗估上限）；可变文本 700 tokens；`max_pixels`=1024² 时单图 1,026 tokens，默认像素时 2,562 tokens；非思考输出 3,000 tokens（参照示例约 1,800 tokens，再上浮）；思考模式额外 +4,000 输出 tokens（估计值，待实测）。单价：输入 0.2 元/百万，输出 2 元/百万；缓存创建按输入价 125% = 0.25 元/百万，命中按约 10% = 0.02 元/百万。

| 场景（2 张图，1024²） | 前缀费用 | 其余输入 | 输出 | **单案例合计** |
|---|---|---|---|---|
| 不命中（无缓存） | 9,000×0.2 = 0.00180 | 2,752×0.2 = 0.00055 | 3,000×2 = 0.00600 | **≈0.0084 元** |
| 首次建缓存 | 9,000×0.25 = 0.00225 | 0.00055 | 0.00600 | **≈0.0088 元** |
| 命中 | 9,000×0.02 = 0.00018 | 0.00055 | 0.00600 | **≈0.0067 元** |
| 3 张图、默认像素、不命中 | 0.00180 | 8,386×0.2 = 0.00168 | 0.00600 | **≈0.0095 元** |
| 3 张图、默认像素、思考模式、不命中 | 0.00180 | 0.00168 | 7,000×2 = 0.01400 | **≈0.0175 元** |

（表中乘积单位为「tokens × 元/百万 tokens」，结果已换算成元。）

结论：**成本大头是输出**（约占 70%～80%），缓存只能省前缀那部分（每案例约 0.0016 元）。规划时取保守单价：非思考 **0.010 元/次**，思考 **0.020 元/次**。50 元可支撑约 2,500 次（全部按思考保守价）到约 6,000 次（非思考、不命中）调用。**预算不是瓶颈，带标注、有授权的评测图片才是。**

### 7.5 统计效力（必须如实说明）

| 结论 | 封存测试集 n=550 | n=400 |
|---|---|---|
| 前三命中 85% 的 95% 置信区间 | 约 ±3.0 个百分点 | 约 ±3.5 个百分点 |
| 首选命中 65% 的 95% 置信区间 | 约 ±4.0 个百分点 | 约 ±4.7 个百分点 |
| 单个大类（约 50 / 约 36 个案例）在 85% 附近 | 约 ±10 个百分点 | 约 ±12 个百分点 |
| 观察到「安全违规 0」时，真实违规率 95% 上界（三分之一法则：3/n） | ≤0.55% | ≤0.75% |

- 整体前三与首选命中可以得出有统计意义的结论。要说「前三命中 ≥85%」有把握，观测值需约 ≥88%，置信区间下界才不低于 85%。
- **单个大类只能作方向性判断，不能作统计结论**；样本少的类别（病毒、线虫）尤其如此。
- 「安全违规 0」只能表述为「在 n 个案例中未观察到违规，真实违规率 95% 上界约 0.55%～0.75%」，**不能证明违规率为 0**；上线后仍需持续监测。
- 预算足以把测试集扩大到 1,000 以上，真正的限制是能拿到多少有授权的标注图片。

1. 每个候选版本 = {模型快照、前缀 SHA-256、Schema 版本、病因表与药剂名单版本、请求参数}，组成不可变版本组，写入策略发布（`diagnosis_releases`）。

## 10. 风险

1. **安全风险上升**：生成式内容可能出现名单外的做法或对特定植物有药害；只能靠名单、正则、词典和评测把关，无法做到 100% 拦截。
2. **准确率风险**：生理性/环境性问题仅凭照片难以区分（浇水过多 vs 根腐 vs 缺氮）。
3. **统计效力有限**：单个大类和「零违规」都无法在评测中被统计证明（见 7.5）。
4. **合同回改面广**：C1～C12 涉及 4 份文档、2 张票、1 份 Schema 和配置目录，需要一次性同步，否则新旧条款会互相矛盾。
5. **缓存效果有限**：输出占成本大头，缓存只能省约 20%；低流量时缓存 5 分钟就失效。
6. **授权数据不足**：生理性、环境性、药害类公开数据集很少，可能拖住评测集建设。

### 12.2 逐类增益分析（定性，待「有/无上下文」对照评测验证）

判断依据：植物病害诊断的常规方法是「看症状 + 问病史 + 看环境」三件事一起看（例如美国各州立大学推广服务的植物诊断流程：先确认植物身份和正常形态，再看症状分布规律，最后结合栽培史与天气）。总的规律是：**病原与虫害的特征主要靠图像，生理性和环境性问题主要靠「病史 + 环境」区分**，因为后者在照片上的表现高度相似（黄化、萎蔫、叶尖焦枯），而成因只能从时间线和环境里看出来。

| 大类 | 能显著提升鉴别的上下文 | 增益 | 理由 |
|---|---|---|---|
| 根部（根腐、盘根） | 近 7～14 天浇水次数与间隔、最近一次盆土观察（湿/干）、基质保水性 + 有无排水孔、盆尺寸、最近一次浇水建议给出的干燥状态 | **高** | 根腐和缺水都表现为萎蔫，最关键的区分点是「土湿还是土干」。照片通常看不到根，档案和浇水记录几乎是唯一线索；无排水孔 + 保水基质 + 高频浇水是根腐的典型风险组合 |
| 生理性（浇水过多/缺水、光照不足、水肿、移栽不适应） | 浇水记录与盆土观察；朝向 + 最近 Lux 读数（光照不足、徒长）；建档/换盆时间（移栽不适应）；近期低温高湿 + 浇水多（水肿） | **高** | 这类问题照片表现高度相似且非特异；病史就是诊断依据本身 |
| 环境性（日灼、冻害、高温、空气过干） | 近 7 天城市短波辐射（**已部署**）、朝向 + 最近 Lux 读数、室内/阳台/户外、城市气候剖面；近期气温（**温湿度接入未上线**） | **高**（日灼）／**中**（冻害、高温：现阶段只有气候态，没有近期实测气温）／低（空气过干：无湿度数据） | 日灼与炭疽、叶斑容易混淆，「近期强辐射 + 南窗/户外 + 斑块在向光面」能明显拉开差距，这些数据现在都有。冻害需要「近期低温」才可信，温度接入上线后可升为高 |
| 营养（缺氮/铁/镁/钾） | 最近施肥记录（**当前缺数据**）、换盆时间、基质类型、浇水是否过多（吸收障碍） | **中** | 缺素图像有一定特征（叶脉间黄化、老叶/新叶先后），但浇水过多导致的吸收障碍会产生同样表现，需要浇水记录来排除；施肥记录缺失会限制增益 |
| 药害/肥害 | 最近施肥/用药记录（**当前缺数据**）、盆土观察中的盐霜 | **中**（如补齐事件）／低（现状） | 药害肥害几乎完全靠「最近做过什么」判断；现有数据没有施肥/用药事件，增益有限 |
| 真菌病害 | 通风（**已有**）、浇水频次、室内/户外、城市气候剖面中的湿润程度；近期湿度（**未上线**） | **中**（温湿度上线前偏低） | 湿度和通风是真菌病的发病条件，可以提高或降低可能性，但病斑、霉层本身仍要靠图像；对白粉病（偏干也会发生）的帮助比对灰霉、霜霉小 |
| 细菌病害 | 近期高温高湿、叶面喷水习惯、冻伤后继发 | **低～中** | 有助于与真菌斑、水肿区分，但主要证据（水渍状、受叶脉限制的多角斑）仍在图像里 |
| 虫害 | 建档/购入时间（新株带虫）、户外/室内、季节；近期是否在附近植物发现同类虫（**当前缺数据**） | **低** | 虫害主要靠看见虫体或典型痕迹；上下文只能提示「新入手的植株要警惕带虫」或「干燥环境叶螨更常见」 |
| 病毒 | 品种（是否天然斑叶）、是否有蚜虫/蓟马史 | **低** | 主要依据是图像中的花叶/环斑和畸形；品种绑定可以帮助排除「天然斑纹」误判，这一点有价值 |
| 线虫 | 几乎无 | **低** | 必须看到根结；上下文帮不上忙 |
| 非问题（正常老化、天然斑纹） | 品种绑定/身份确认、植物年龄与建档时长 | **中** | 品种确认后能识别「天然斑叶」，减少误报；「只有底部老叶少量黄」配合稳定的养护记录，更容易判为正常老化 |

**汇总**：收益最大的是**根部、生理性、环境性中的日灼**三类（冻害要等温度接入上线后才能达到同等水平）。它们恰好是纯图像最弱的地方：照片相似，成因藏在病史里（v1 用黄叶/萎蔫固定题包问出这些信息，长期植物则可以直接从记录里取，少问几题）。营养和药害/肥害有中等潜力，但受制于缺少施肥/用药事件数据。虫害、病毒、线虫基本靠图像。

**预计提升幅度（定性判断，未经评测）**：

- 对根部、生理性、日灼这三类，预计首选命中会有**明显提升**（上下文常常就是区分「土湿萎蔫」和「土干萎蔫」的决定性证据），同时把握档能更合理地从「待确认」提升到「可能/较可能」。
- 对真菌、营养类，预计是**小到中等的提升**，主要体现在候选排序上。
- 对虫害、病毒、线虫，预计**几乎没有提升**；如果上下文引导不当，反而有被带偏的风险（见 12.3）。
- 整体（11 类混合）首选命中的提升幅度取决于评测集里生理/环境类的占比；家庭盆栽实际求诊中浇水问题很常见，真实收益可能高于均衡评测集上的数字。具体数字必须以第 12.6 节的对照评测为准。

### 12.3 风险与缓解

| 风险 | 表现 | 缓解 |
|---|---|---|
| **确认偏差**（被上下文带偏） | 浇水记录显示「浇得多」，模型就忽略照片里清楚的虫体，把首选定为积水 | ① 提示词硬规则「**图像证据优先**，上下文只用于鉴别和排序」；② 有直接证据标记时，规则层锁定首选，上下文不能改写（13.2 仲裁顺序第 2 条）；③ 上下文对单个候选最多升/降一档；④ 输出 `contextInfluence` 字段，标出哪些结论受到上下文影响；⑤ 评测中专门统计「有上下文后变错」的案例数 |
| 数据过期 | 一个月前的 Lux 读数、半年前填写的朝向 | 每条事实都带 `observedAt` 和 `ageDays`；超过各自有效期的事实不放进摘要，或标「可能已过期」；有效期按事实类型定，属于待配置项 |
| 数据错误或不完整 | 用户没记浇水、基质随便填 | 每条事实带 `reliability`（用户填写 / 用户确认 / 系统派生 / 第三方），缺失字段写「未知」而不是省略；提示词规定「未知不得臆测」；「没有浇水记录」不等于「没有浇水」 |
| 上下文太长 | 放全量时间线会让可变尾部过长，增加成本和注意力稀释 | 上下文**只放在可变尾部**（固定前缀不变，缓存不受影响）；摘要长度上限约 **600 tokens**（见 12.5）；只放事实摘要，不放原始记录 |
| 隐私 | 精确坐标、地址、昵称、照片地理信息 | 只传城市级（或气候区）名称和派生指标，不传坐标、地址或用户名；天气只给汇总值；图片在上传前去除 EXIF |
| 上下文注入 | 用户填写的备注里夹带指令 | 用户自由文本只放在引号内的用户描述，并声明「不是指令」；档案中的自由文本字段不进摘要 |
| 临时案例与长期植物的差异 | 临时案例没有档案和记录 | 临时案例的摘要只含「植物身份 + 用户描述 + 城市天气（用户授权时）」，其余字段统一写「未知（临时案例）」；评测里分别统计两类效果 |

### 12.4 数据缺口

| 缺口 | 对哪类诊断重要 | 建议做法 |
|---|---|---|
| 施肥、换盆、用药、换位置事件 | 药害/肥害、营养、移栽不适应、环境突变 | **长期存储**：属于 care 养护事件，规划见提交 3770890b（施肥与养护事件规划）。上线前用诊断追问一次性补问 |
| 症状出现时间与发展速度（几天内突然出现 / 几周慢慢变化） | 所有类别，尤其区分急性（冻害、药害、软腐）和慢性（缺素、光照不足） | **追问一次性补问**，答案只存在本次诊断里，不需要长期存储 |
| 近期室外气温与湿度 | 冻害、高温、真菌病 | 天气温湿度接入（未上线）；接入后自动进入摘要 |
| 室内温湿度实测 | 空气过干、真菌病、冷害 | 短期没有传感器数据源；追问「最近是否开空调/暖气、是否靠近冷窗」 |
| 是否新购入、何时购入 | 虫害带入、移栽不适应 | 建档时间可以近似；追问一次即可 |
| 附近其他植物是否有同样问题 | 虫害、真菌病传播 | 追问一次即可 |
| 可食用性 | 用药安全门 | 百科字段（未上线）；上线前一律按「未知」处理 |
| 诊断反馈（是否好转、复诊结果） | 规则积累（第 13 节） | 新增合同字段（见 13.4） |

**原则**：会被多个功能反复使用的事实（养护事件、天气）长期存储；只对本次诊断有用的信息（症状出现时间、附近植物情况、空调使用）只在本次追问里问，不长期保存，以减少用户填表负担和隐私面。

### 12.6 评测：「有上下文 vs 无上下文」对照组

**构造带上下文的评测样本**：公开图片本身没有病史，所以上下文要按标注病因**人工编写**，并刻意做成三种情形：

| 情形 | 比例 | 示例 | 检验什么 |
|---|---|---|---|
| 一致上下文 | 50% | 根腐图 + 「近 7 天浇水 5 次、无排水孔、盆土观察：湿」 | 上下文能否帮模型更准、把握更合理 |
| 中性上下文 | 25% | 虫害图 + 正常浇水记录 | 不相关的上下文会不会造成干扰 |
| 冲突上下文 | 25% | 清晰的粉虱图 + 「近 7 天浇水 6 次」 | **确认偏差**：模型会不会被浇水记录带偏，丢掉图像证据 |

- 上下文由两人独立编写并互审，必须符合园艺常识，不能编出「只有这个病因才可能」的作弊式线索（例如直接写「疑似根腐」）。
- 优先选择**高增益类别**（根部、生理性、环境性），并保留少量低增益类别（虫害、病毒）来测干扰。
- 正式评测集如果能拿到经授权的 v1 线上用户案例，可以用真实档案和养护记录替代人工编写，效果更可信（D10 的授权问题同样适用）。

**预算分配**（在原 50 元计划内调整，见 §7.3）：

| 轮次 | 调用 | 保守单价 | 费用 |
|---|---|---|---|
| 开发集对照：选 100 个案例（高增益类 70、低增益类 30），同一案例分别以「无上下文」「一致/中性/冲突上下文」各跑 1 次 → 每案 2 次 | 200 | 0.010 | 2.0 元 |
| 封存测试集对照：选 150 个案例，每案 2 次（只在最终版本跑） | 300 | 0.020 | 6.0 元 |
| 小计 | 500 | | **8.0 元** |

新增约 8 元，可从原计划约 17.3 元的余量里支出；调整后保守合计约 40.7 元，仍在 50 元上限内。为了守住 40 元强制停止线，把开发集迭代从最多 6 轮压缩到最多 5 轮（节省 2 元），调整后保守合计约 **38.7 元**，余量约 11.3 元。上下文文本使可变部分增加约 600 tokens，对每次调用的成本影响约 +0.00012 元，可以忽略。

**统计口径**：

- 主要指标：在高增益类上，「有上下文 − 无上下文」的首选命中差值，用**配对**比较（同一案例两种条件），比非配对比较需要的样本少得多。
- 安全指标：冲突上下文组里「图像证据清楚却被上下文改错」的比例，目标为 0，并在报告中逐例列出。
- 样本限制：开发集 100 个配对案例，大约能分辨 10 个百分点以上的差异；更小的提升需要更多样本，只能作为方向性结论。

### 13.2 「生成式 + 规则」分工

| 层 | 负责 | 不负责 |
|---|---|---|
| **模型** | 看图描述可见证据（输出闭集证据标记 + 中文观察）；生成 ≤3 个候选病因编号与把握档；按首选候选写完整中文内容（诊断表、识别依据、四分区处置） | 不决定是否放行；不决定最终首选能否被规则改写；不产生规则 |
| **规则层**（确定性代码 + 规则集发布） | ① 安全门（不给剂量、药剂名单、可食用间隔期、高风险理由、证据不足不下结论）；② 高特异性直判（直判证据组命中 → 锁定首选、零追问）；③ 矛盾检测（如候选为「缺水」但最近盆土观察为「湿」且 24 小时内浇过水 → 标记冲突、降档或追问）；④ 排除规则（如未拍到根部时「线虫」不得为「较可能」；品种已确认为天然斑叶时「病毒花叶」需额外证据）；⑤ 上下文鉴别加权（如「近 7 天浇水 ≥N 次 + 无排水孔 + 保水基质 → 根腐/积水风险加权」，N 等阈值进规则集，不写死在代码里） | 不写用户可见文案；不新增病因编号 |
| **服务端编排** | 组装上下文摘要；调用模型；执行规则；按仲裁结果投影公开 DTO；记录模型版本组 + 规则集版本 | — |

**最终判决权与仲裁顺序**（从高到低，前者否决后者）：

1. **规则安全门**：违反即整份拒绝或删除对应步骤，任何层都不能覆盖。
2. **高特异性直判规则**：命中时首选候选由规则锁定。如果模型的首选不同，以规则为准，并要求模型内容与之一致（不一致则重试一次；仍不一致就降级为「可能」并提示补拍）。
3. **矛盾检测 / 排除规则**：可以把模型候选降档、移出首位或触发追问，但不能凭空新增模型没给的候选（防止规则写出模型没有依据的内容）。
4. **上下文鉴别加权**：只调整模型候选之间的**排序和把握档**，单次最多升/降一档。
5. **模型候选排序**：其余情况以模型为准。

规则改动了模型结论时（2～4 项），公开结果里的「识别依据」要追加一条服务端生成的说明，例如「结合近 7 天浇水记录，积水可能性更高」，并在内部记录「规则 X 版本 Y 改写了首选」，便于复算与评测。

### 13.3 模型辅助积累规则的闭环（核心）

前端类比：类似「埋点 → 数据看板 → 提需求 → 评审 → 灰度 → 全量」。模型相当于帮你看数据、写需求草稿的分析师，**它不能直接上线代码**。

```text
① 采集（线上诊断结构化结果 + 用户反馈 + 评测集标注）
      ↓ 只存编号、档位、上下文摘要的分桶值，不存原图地址/原文
② 挖掘（离线统计「证据组合 → 病因」支持度/置信度/提升度；模型把高频高准模式整理成候选规则，或对照文献生成候选）
      ↓ 候选规则 = 条件表达式 + 依据样本数 + 反例 + 来源
③ 审核（人工或园艺来源审核：依据、反例、适用范围、风险）
      ↓ 通过
④ 影子模式（只记录「如果启用会怎样」，不影响用户结果）
      ↓ 影子期命中率、误伤率达标
⑤ 发布（规则集策略发布：类型化 Schema、不可变版本、SHA-256、active 指针、可回滚）
      ↓
⑥ 运行与复算（诊断结果记录规则集版本；回放按原版本复算）→ 回到 ①
```

**① 数据来源与字段**

| 来源 | 字段 | 噪声与处理 |
|---|---|---|
| 线上诊断结构化输出 | 证据标记（directMarkerKeys）、逐图部位与质量、候选病因编号与把握档、规则命中记录、上下文摘要的**分桶值**（如「近 7 天浇水次数：3～4」「基质保水：高」「朝向：南」）、版本组、规则集版本 | 只用闭集编号和分桶值，便于统计，也避免把原文和隐私带进规则仓库 |
| 用户反馈（**需新增合同**） | ① 是否采纳某条建议（care 确认事件已有，可关联）；② 复诊结果（同一用户植物 N 天内再次诊断的首选编号）；③ 主动反馈「好转/无变化/恶化」；④ 用户纠错「实际是 X」（可选） | 反馈是**弱标签**：好转不等于诊断正确（可能自愈，也可能是同时改了别的养护）；只作为加权信号，单独不足以确立规则 |
| 评测集标注 | 两人复核的病因编号 | **强标签**，规则准入主要依据 |
| 文献 / 园艺来源 | 典型证据组合与鉴别要点 | 冷启动主要来源；须挂来源主张 |

**② 挖掘方法**

- 把每次诊断整理成一条「事务」：`{证据标记…, 上下文分桶…} → 标注病因`。标注病因优先用强标签（评测集、专家复核）；弱标签（复诊一致、用户好转）只作补充，并单独统计。
- 对每个「条件组合 → 病因」计算：
  - **支持度**：该组合出现的样本数，要求 ≥ 最小样本量门槛（建议 30）。
  - **置信度**：组合出现时，病因为 X 的比例，即 P(X | 条件)。
  - **提升度**：置信度 ÷ 病因 X 的基础比例。大于 1 说明这个组合确实提高了 X 的可能性；建议 ≥2 才考虑。
  - **反例**：组合出现但病因不是 X 的样本，抽样给审核人看。
- 模型的作用：把统计结果翻译成可读的候选规则（条件表达式 + 中文说明 + 依据样本数 + 反例摘要），或者对照文献补充「应该存在但样本还不够」的候选。**模型生成的只是草稿。**

**③ 审核**：每条候选规则必须带①条件表达式、②依据（统计数字或文献来源）、③反例、④适用范围（植物科属、室内/户外）、⑤作用类型（直判 / 排除 / 加权 / 矛盾检测）、⑥风险评估。审核人可以是团队园艺负责人或外部顾问；涉及用药或高风险行动的规则必须有园艺来源。

**④ 影子模式**：规则以「影子」状态运行，只记录「若启用会改变首选/档位的案例」。达到以下条件才允许发布（数值为推荐，待拍板）：

- 影子期内触发 ≥50 次；
- 在有强标签的样本中，规则改写后的准确率 ≥ 改写前，且误伤率（把对的改错）≤5%；
- 没有安全违规。

**⑤ 发布**：规则集作为独立的业务策略发布（BusinessPolicyRelease，拟命名 `diagnosis.visual_rules`）：类型化 TypeScript 类型 + AJV Schema、不可变 release、SHA-256、active 指针、回滚审计。规则条件只能引用闭集证据标记、上下文分桶字段和病因编号，**不允许写任意代码或正则**（防止规则集变成第二个规则引擎黑箱）。每次诊断结果记录规则集版本，历史结果可按原版本复算。

**⑥ 防污染**

| 风险 | 控制 |
|---|---|
| 模型输出直接变成规则 | 禁止：候选规则必须经过统计依据或文献依据 + 人工审核 + 影子期 |
| 自我强化（模型的诊断结果被当作标签，再挖出「支持模型」的规则） | 挖掘时**不用模型自己的首选当标签**；只用强标签（评测集、专家复核）和与模型无关的弱标签（复诊、用户反馈）。弱标签规则必须在强标签样本上复核通过 |
| 用户反馈噪声 | 反馈只加权不定案；同一用户植物只计一次；明显异常（一天内反复改口）丢弃 |
| 分布偏移（如季节变化） | 规则按季节/地区分桶统计；发布后持续监控命中率，下降就回到影子模式 |
| 小样本假规律 | 支持度门槛 + 提升度门槛 + 反例审查；冷门病因宁可没有规则 |
| 规则膨胀互相冲突 | 发布前做冲突检测（同一条件指向不同病因时必须明确优先级）；规则总数和单条规则的作用幅度设上限 |

**与现有架构对齐**

- 数据归属：训练事务只来自 `user_id + user_plant_id` 的诊断结果或临时案例；挖掘用的数据集是**脱敏衍生表**（不含 user_id、图片地址、原文，只保留分桶值和编号），按保留期策略管理。
- 用户授权：使用线上诊断数据挖掘规则，需在用户协议中说明「用于改进诊断质量」，未授权的样本不进入挖掘。
- OpenViking 只记录「规则治理流程已确立」这类稳定决策，**不作为规则仓库**；规则的唯一事实源是策略发布。
- 配置目录需新增：`diagnosis.visual_rules.release_ref`（规则集发布引用，待冻结）、`diagnosis.visual_rules.shadow_promotion_thresholds`（影子转正门槛，待冻结）、`diagnosis.visual_rules.mining_min_support`（最小支持度，待冻结）。
- 规则集不能放宽安全门：安全门属于不可配置硬规则，规则集只能在其内部调整候选排序和档位。

### 13.4 可行性与收益评估

**冷启动（还没有线上数据）**：靠文献、v1 已审计规则和评测集起步。

| 来源 | 预计规则数 | 内容 |
|---|---|---|
| v1 已审计直判证据组 + 快速通道 | 约 13 条 | 8 类虫害 + 白粉病 + 煤污，改写为规则集格式 |
| 新增高特异性直判（文献明确） | 约 8～12 条 | 锈病孢子堆、灰霉绒毛、潜道 + 虫粪、盐霜 + 叶尖焦枯、褐黑软烂根等 |
| 排除规则 | 约 10～15 条 | 未拍到根不判线虫/根腐为「较可能」；已确认天然斑叶品种时病毒需额外证据；不可用图片不出候选等 |
| 矛盾检测 | 约 5～8 条 | 缺水 vs 盆土观察为湿；冻害 vs 近期无低温（温度接入后）；日灼 vs 背光面等 |
| 上下文鉴别加权 | 约 10～15 条 | 浇水频次 + 排水 + 基质 → 积水/根腐；辐射 + 朝向 → 日灼；建档时间短 → 移栽不适应/带虫等 |
| **合计** | **约 45～65 条** | 全部需人工/园艺审核，首批建议 30 条左右先上影子模式 |

**积累新规则需要多少数据**：

- 门槛：一条规则需要 ≥30 个带**强标签**的支持样本，且提升度 ≥2。
- 线上诊断里能拿到强标签的比例很低（需要专家复核或评测集）。粗略估计：若每月有 1,000 次诊断，每月抽样 5%（约 50 例）做专家复核，再加上 10%～20% 有用户反馈的弱标签，常见病因（浇水问题、叶螨、粉虱、白粉病）大约 **3～6 个月**能积累出第一批有统计意义的新规则；冷门病因（病毒、线虫、细菌）可能需要一年以上，或者始终依赖文献规则。
- 也就是说，**模型辅助积累规则是中长期收益**：前 3～6 个月主要靠冷启动规则和模型本身，规则挖掘主要用于发现「模型的系统性错误」（例如持续把水肿判成介壳虫），再用排除或矛盾规则修正。
- 这些都是在没有线上数据时的估计，需要上线后用实际诊断量和反馈率重新测算。

**现有诊断会话存储够不够**：

| 需要的字段 | 现状 | 缺口 |
|---|---|---|
| 版本组（模型、提示词、Schema）引用 | v2 已有 `diagnosis-model-binding` 与结果回放记录合同 | 需增加 `diagnosis-visual-gen/*` 版本组 |
| 证据标记、候选编号、把握档 | 现有结果记录以 v1 题包和证据为中心 | 需新增生成式结果的结构化存储（候选编号、直判标记、逐图部位与质量） |
| 规则命中记录与规则集版本 | 无 | **需新增**：每条命中规则的 ID、版本、作用（锁定/降档/排除） |
| 上下文摘要分桶值 | 无 | **需新增**：12.5 摘要的 key + 分桶值（不存原文） |
| 用户反馈（好转/无变化/恶化、纠错） | 无（协调方确认「诊断反馈字段未上线」） | **需新合同**：反馈事件归属 `user_id + user_plant_id`，带诊断结果引用和时间 |
| 复诊关联 | 可以通过同一用户植物的诊断历史推出 | 需定义「复诊」窗口（待配置） |
| 建议是否被采纳 | care 用例的确认事件已有 | 需在 care 事件里引用来源诊断结果 ID（内部引用，不外露） |
| 专家复核标签 | 无 | **需新增**内部复核表（可复用 v2 诊断 review 记录合同的思路） |

### 14.1 首版是否必须先采集反馈数据？（论证与最小方案，供协调方询问用户）

**结论：建议首版就采集「最小反馈」，但不建规则层。** 理由：

1. **规则挖掘需要回头看的数据，而数据没法事后补**。中长期第一批规则需要约 3～6 个月的带标签样本（13.4）。如果首版不记录，规则层上线时只能从零开始积累，相当于白白推迟 3～6 个月。
2. **首版本身也需要它**：受约束生成式没有规则兜底，线上质量只能靠反馈发现系统性错误（例如持续把水肿判成介壳虫），以便迭代提示词。
3. **成本很低**：大部分字段在首版已经必须存（版本组、结构化结果用于回放与脱敏投影）；真正新增的只有一个轻量反馈事件。

**最小方案**（只多 1 张表、1 个写接口，不做挖掘、不做复核后台）：

| 项 | 内容 | 首版是否已有 |
|---|---|---|
| 结构化结果留存 | 候选病因编号、把握档、直判标记、逐图部位与质量、上下文摘要的键与分桶值、版本组 | 大部分已因回放与投影而必须保存；需确认上下文分桶值一并保存 |
| 采纳关联 | care 确认事件里记录来源诊断结果（内部引用，不外露） | 需在 care 确认用例里加一个可选引用字段 |
| 一键反馈 | 结果页「有帮助 / 没帮助」，以及 7～14 天后可选的「好转 / 无变化 / 恶化」；归属 `user_id + user_plant_id`，一个诊断结果只保留最新一次反馈 | **新增**：`diagnosis_feedback` 表与写接口（幂等：同一诊断结果覆盖写） |
| 数据使用授权 | 用户协议写明「用于改进诊断质量」 | 需法务/产品确认文案 |

不在最小方案内：用户纠错「实际是 X」、专家复核抽样、规则命中记录、挖掘衍生表——都随规则层一起做。

- 当前评分**还不能衡量「该追问时追问了」**：没有上下文的生理/环境类案例，按产品设计本来就应该追问而不是硬判。下一步要在评分里加「追问质量」指标：证据不足时是否在追问里问到了能区分病因的环境信息，以及「证据不足 + 有效追问」是否计为合理结果。
- 4 例变化里至少有 1 例是随机波动，样本只有 29 个，**两版的差距不具备统计意义**。
- 结论：v1.1 先作为候选保留，不替换 v1；等追问质量评分上线后，在开发集（200 个案例，有/无上下文）上重新比较。

**解读**：

## 附：给前端同学的术语对照

| 后端说法 | 前端类比 |
|---|---|
| 提示词缓存（前缀缓存） | 浏览器强缓存带 hash 的 `vendor.js`：前缀不变就命中，改一个字节就要全部重新下载 |
| 固定前缀 / 可变部分 | 打包出来的公共 chunk / 每个页面自己的业务 chunk |
| 编号先行 + 安全门 | 接口返回的每段富文本都带 `type` 字段，前端拦截器先按 `type` 和规则校验，不合规整条丢弃 |
| 闭集编号 | TypeScript 字面量联合类型，不在列表里就类型报错 |
| Schema if/then | 表单联动校验：勾了「用药」，「按标签提示」就必填 |
| 策略发布 + active 指针 | 灰度发布：多个版本并存，指针指向谁就用谁，回滚只改指针 |
| Adapter / Provider Registry | 封装好的 `request` 层：业务只调 `api.diagnose()`，不关心后面是哪家、密钥放在哪 |
| Proposal → care 确认 | 表单草稿：诊断只生成草稿，用户点「保存」才真正提交到养护记录 |
| 置信区间 | A/B 实验报告里的「显著性」：样本太少时，85% 和 75% 可能分不出差别 |
