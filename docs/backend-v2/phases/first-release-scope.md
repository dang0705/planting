# 青花植首版运行边界

> 唯一目标：在完整目标业务架构不变的前提下，交付并验证“第一次解决植物问题 → 保存/绑定我的植物 → 后续养护与复访”的最短闭环。产品主张是 **Everything is for your plant**。本文件是 Master Plan 的首版执行范围，不创建第二套业务架构；具体实施仍须从对应 Phase、合同和 ClickUp ticket 进入。

本文件只决定首版开放范围和实施先后，不要求为目标架构中的每个节点分别开发一条纵向切片。跨域端到端验收只围绕实际开放的用户主旅程及其关键风险；其他能力按所属业务合同和必要测试验收，不为填满架构图而实现。**识别缺口自动 CMS 扩种、CMS 拓百科及其贡献奖励首版延后；已建基础百科表通过验收后可只读展示。** 多图证据、小青只读试运行等受控实验仍需在对应票据确认成本、质量和开关，不能因出现在架构图中自动启动。既有已冻结合同不因运行范围收敛而失效。

## 首版实施顺序

| 顺序 | 首版要交付什么 | 本轮后端工作的边界 |
|---|---|---|
| 先取得第一次价值 | 游客可使用已审核植物识别，以及黄叶、萎蔫、虫害的基础问诊；结果有依据、可执行行动和不确定性说明 | 优先接通已发布身份只读与基础诊断；不等待基础百科数据集完成、CMS 扩种、多图或小青。基础百科验收通过后可并入只读体验。浇水是首版目标；模型结构已经冻结为 Baseline → EnvironmentDemand / CultivationRetention / PersonalCalibration → DryUnit/DryProgress → Soil Safety Gate。当前只剩参数校准、DDL/Repository 对齐与真实链路验收；Watering 一级决策不得使用 `indoorEqHours` / `dryDownFactor` |
| 再建立长期关系 | 微信先行完成真实登录；游客或已登录用户的临时案例，经本人明确选择后创建或绑定用户植物；必要结果可认领，后续记录归属该植物 | 优先完成登录、用户植物创建/读取、归属校验与必要认领合同；只验证这条跨域主旅程，不要求每个架构模块各做一条独立纵向切片 |
| 然后支持复访 | 必要档案、真实养护事实、状态、简要时间线与有意义的后续提醒/反馈 | 只做能支撑下一次照顾同一株植物的最小运行子集；成长玩法、复杂计划与大规模历史搬迁延后 |
| 最后验证付费价值 | 免费、一次性 24 小时试用、会员和生成式 AI 额度按能力资格统一判定；诊断解释可在安全底线之上受控增强 | 先证明权限和成本边界，再开放收费或实验；额度的上线故障级加固不抢在核心旅程前面。积分不进入首版 |

这四行表示**同一首版的开发优先级**，不是要求拆成四次公开发布。某能力若缺少必要合同、模型或真实链路证据，只阻断该能力的开放；不能把未验收能力悄悄换成旧算法，也不能让它自动阻断已经独立验收的主链。诊断的基础内容底线不能由生成式实验代替。

## 状态含义

| 状态 | 首版含义 | 后续要求 |
|---|---|---|
| 核心稳定 | 首版运行且合同、归属、安全和失败路径均验收 | 按完整验收门上线 |
| 收敛上线 | 首版运行必要子集，使用既有稳定合同 | 未运行子集留在目标架构和后续任务中 |
| 受控实验 | 可以灰度运行；有成本上限、可关闭、可回滚、可观察 | 证据通过后才转稳定；失败时回到安全基线 |
| 延后 | 保留目标节点和高代价核心契约，首版不对用户开放 | 不得把未实现标为 ticket 完成 |

## 从入口到用户植物的首版闭环

```text
识别 / 黄叶、萎蔫、虫害问诊 / 独立浇水
→ 游客临时植物，或已登录用户主动选择临时植物
→ 获得有证据的结果与可执行建议
→ 用户选择保存：游客先登录，已有 user_id 的用户直接选目标
→ 创建新用户植物或绑定已有用户植物
→ 同会话必要结果一次性认领；建议仍是建议，真实行为须用户确认
→ 用户植物事实、状态、时间线与基础提醒
→ 再次养护、问诊和反馈
```

游客第一次进入植物业务只能走临时上下文。已有 `user_id` 的用户可主动选择临时上下文，不能因为已登录就自动写进已有植物。识别候选不能自动成为正式植物身份；用户植物归属校验和认领审计从首版起稳定。完整旧会话、图片和跨设备历史搬迁延后。游客同会话必要结果按[游客会话认领合同](../contracts/guest-session-claim.md)执行；已登录用户的临时案例须先通过[合同补充门](../contracts/authenticated-ephemeral-plant-case.md)，不能直接套用游客证明或 DDL。

## 按架构节点确定首版运行状态

首个真实平台登录切片选择微信小程序。此处仅确定实施顺序；统一 `user_id` 和其他平台身份的目标架构不变，其他平台不得因微信先行而使用微信主体作为业务主键。

| 目标节点 | 首版状态 | 首版交付边界 |
|---|---|---|
| Visitor、统一 `user_id`、平台身份、能力判定 | 核心稳定/收敛上线 | 游客/登录身份与能力资格分开；微信先行，其他平台保留统一主体合同。24 小时试用、会员与 AI 额度仅实现首版开放所需的判定和扣减，不以完整账本的灾难恢复能力作为第一条用户旅程的前置条件 |
| 植物业务入口、临时/长期作用域 | 核心稳定 | 先判断主体，再由登录用户选择临时或长期；同会话保存必须显式确认 |
| 用户植物、植物身份、个体档案 | 核心稳定/收敛上线 | `user_plant_id` 为长期数据中心；首版只采集必要档案与经确认的身份 |
| 原子环境、栽培配置、运行时植物上下文 | 核心稳定/收敛上线 | 保留来源、空间范围、时间与版本；仅渐进采集参与首版算法的数据 |
| 真实事实、状态投影、时间线 | 核心稳定 | 事实、诊断、建议和计划语义分离；时间线数据层上线，丰富展示延后 |
| 百科详情 SQL 主读 + 内部身份准入 | 收敛上线目标 | 2026-10-03：百科详情运行时主读为 `qinghuazhi_v2_test.tropicals_species_encyclopedia_ref`（及相关离线 `tropicals_*`），slug 由学名去符号生成 kebab-case。实时 API 不是主来源。代码仍仅首页 PlantSearchToolbar 直连 API，SQL 只读尚未完成。外部 id/slug/SQL 行未经 crosswalk 不能等同内部身份或已确认用户身份 |
| SQL 百科详情与媒体 | MVP 展示目标 / 逐项许可 | 详情读百科表已有列；缺 nameEn、COL、价格等 API 字段不阻断。文本按数据集/来源署名，图片逐项核对许可。目录搜索目标表是已在库内的 `plant_search_*`，并已冻结独立 `plant-catalog-search/v1` API 合同；首页代码仍走 Tropicals 自动补全，尚未接线。已发布身份公开搜索合同保持独立。展示型外部养护、环境与病虫害文本不进入养护/诊断规则；结构化性状证据须经 plant-knowledge 审核发布后才能进入 Internal Care Knowledge |
| CMS 自动扩种、生成式拓百科、百科贡献奖励 | 延后（已确认） | 首版不运行内部身份自动补缺、不用 Qwen 生成百科草稿、不开放 CMS 百科扩展和此类贡献奖励；该治理延后不阻断 SQL 百科详情只读 |
| 浇水与盆土安全门 | 首版目标 / 结构已冻结，参数与链路待验收 | 采用 `watering-decision-model/v1`：BaselinePolicy + GrowthActivity + DLI/Air VPD/AirMovement + CultivationRetention + PersonalCalibration → DryUnit/DryProgress → 当前 Soil Gate。`indoorEqHours / dryDownFactor` 不属于正式一级决策输入；未完成真实 HTTP/MySQL/Provider 与影子校准前不得声称已上线 |
| DLI、Estimated Indoor、Air VPD 等派生 | 正式上游结构已冻结 / 参数待验收 | 光照固定走 DNI/DHI/GHI → 太阳几何 → 窗面 Direct/Diffuse → PPFD → DLI；室内 T/RH 实测优先，缺失时只能显式估算后再算 Air VPD。具体透射/敏感度参数仍需影子数据与 release 验收 |
| 光照、通风评估 | 目标架构保留；光照模型结构已冻结 | DLI/PPFD 是正式光照确定性链；是否单独开放“光照顾问”不影响其作为浇水上游。通风保留原子事实及稳定输出合同；室外风速不得等同室内通风，AirMovement 最终敏感度仍待校准 |
| 完整施肥规划 | 延后 | 保留领域和输出合同，首版不以施肥完整运行作为上线门槛 |
| 黄叶、萎蔫、虫害诊断及行动建议 | 核心稳定 | 固定/动态题包和证据账本；黄叶沿用 v1 四题采证与答案分流的业务逻辑，完整作答可得到一个或多个候选方向，不得一律降级为待判定；症状入口与园艺原因分轴；Outcome（诊断结论）和 Action（行动建议）来自 CMS 已审核的兼容发布包。结果须区分依据与不确定性、可执行的检查/处理步骤、暂不做的动作和复查条件。仅在证据不足或冲突时补问或待判定；旧分数、行动文案、来源状态及旧浇水/光照派生证据不得未经审核直接作为 v2 已发布规则 |
| 多图证据、生成式丰富解释 | 受控实验 | “诊断内容和行动建议更充实”是首版产品目标；实现必须遵守[诊断内容实验合同](../contracts/diagnosis-rich-response-experiment.md)。候选未过成本/质量门可回退保安全，但不得冒充该产品目标已验收 |
| 小青只读解释与引导 | 受控实验 | 使用受控植物上下文；正式业务写操作延后，不能绕过用户确认 |
| CMS 草稿、审核、版本发布、回滚 | 收敛上线 | 首版仅承担题包、园艺原因、结论、行动建议及其他已明确必需内容的审校发布；不因诊断依赖 CMS 而重新开放植物扩种或 CMS 拓百科链路。基础百科数据集只读发布另行验收 |
| 积分、养护等级、积分兑换 | 延后 | 目标合同和已经完成的内部代码保留；首版不开放积分入口、不发积分和等级额度、不要求兑换验收 |
| CMS 扩种/百科贡献 AI 奖励 | 延后（已确认） | 随扩种与百科在后续阶段独立验收；首版不发放，不混入积分 |
| 环境分区、成长玩法、复杂计划 | 延后 | 不改变用户植物、事实、计划及时间线的核心语义 |

## 首版验收与阶段关系

- MVP 百科详情以 CloudBase SQL `qinghuazhi_v2_test.tropicals_species_encyclopedia_ref` 为主读，不以 Tropicals 实时 API 为运行时主路径；当前仅首页 PlantSearchToolbar 仍直连 API，SQL 只读尚未完成。数据集署名与图片逐项来源许可必须分别落实。目录搜索目标是库内已有的 `plant_search_*`，不是认定该投影不存在；首页尚未改读它。已发布身份仍用公开搜索合同。俗名不是唯一键，重名全留。搜索命中、SQL 行或 API 命中不能自动升格成内部身份。缺失内部映射不阻断百科详情只读，但内部 PlantIdentity/Taxon 发布仍须来源、歧义、完整父链、人工审核和发布读回。诊断知识 CMS 仍是首版独立必要链路。关系见 [植物目录数据模型](../architecture/plant-catalog-data-model.md)。
- P1 内部身份 seed 继续按既有 106 条逐条证据与准入推进；来源记录 29、73、98、123 继续隔离。该名单只决定对应内部 PlantIdentity/Taxon seed/release 的资格，不能阻断 SQL 百科详情只读或符合许可的媒体展示。百科行或 Tropicals 命中也不能直接发布内部身份；数据库导入、人工审核、发布与公开读取仍须独立验收。
- P-1/P0/P1 的架构、身份准确性、权限、数据字典、合同和安全门继续作为对应能力的前置条件，不因收敛首版而放松。生成式诊断增强的供应商成本与动作上限未冻结时仅阻断该增强候选，不自动阻断已独立达到内容底线的基础诊断；基础诊断仍须满足可执行、可复查的内容验收。
- 已登录用户临时植物属于首版核心路径。公共语义已冻结为 `authenticated-ephemeral-plant-case/v1`，采用游客/登录两套 backing case、统一 `ephemeralPlantCaseRef` 语义；TTL、迁移 DDL 与真实链路验收完成前仍不得宣称运行闭环。
- P2–P6 中的任务分别标注“首版运行验收”与“目标架构后续实现”。延后能力可保留合同或已有代码，但本轮不得仅因存在架构节点就新开功能切片；也不能因代码存在就视为首版开放，或因首版不开放就删除目标节点。
- 首版门槛以真实 HTTP、MySQL、CloudBase/Provider 可验证路径和前端另阶段接入为准。后端仅通过本阶段验收时，结论仍为“后端服务验收通过，等待前端接入”。
- ClickUp 任务若同时覆盖首版与延后范围，应拆出可独立验收的后续任务或明确子验收项；不得把部分完成票据标成 `done`。运行状态、证据与进度页须一致。
- 首版检验一次使用是否能转化为用户植物的长期关系：开始→完成识别/问诊/浇水→创建或绑定植物→产生下一次有意义的记录/复访，并单独记录 AI 单动作成本与额度消耗。指标只定义口径，不在缺少真实数据时预设成功率。
- 诊断内容底线由独立 Expected 和黄叶、萎蔫、虫害代表样本验收；生成式增强可以改进表达，但不能代替底线。增强失败回退后若基础结果未达到该底线，诊断产品目标仍未验收，须继续改进或由用户明确裁决取舍。
