## 1. 案例清单字段（每个案例一行，存在仓库外的评测目录，不入 git）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `caseId` | 字符串 | 是 | `D001`～`D200`；与图片文件名前缀一致 |
| `images[]` | 数组 | 是 | 1～3 张；每张含 `file`、`visiblePart`（与提示词枚举一致）、`sha256` |
| `source` | 枚举 | 是 | `S1_induced`（受控诱发）、`S2_user_authorized`（授权用户图）、`S3_schlaghecken`、`S4_scot_nelson`、`S5_starr`、`S6_commons_category`、`S7_inaturalist`、`S8_plantvillage` |
| `sourcePage` / `author` / `license` / `licenseUrl` | 字符串 | 公开来源必填 | 逐张核验；`S1` 写「自有」；`S2` 写授权记录编号 |
| `plantIdentity` | 字符串 | 否 | 规范中文名与学名；不确定写「未知」 |
| `edible` | 枚举 | 是 | `yes` / `no` / `unknown`；决定用药是否必须提示安全间隔期 |
| `setting` | 枚举 | 是 | `indoor_pot`（室内盆栽）、`balcony_pot`、`outdoor` |
| `primaryCauseCode` | 闭集编号 | 是 | 取自提示词【4】的 50 个病因编号；无法确定的不入开发集 |
| `acceptableCauseCodes[]` | 数组 | 是 | 可接受的命中编号（含主因；多病并存时含次因） |
| `evaluationGroup` | 枚举 | 是 | `image_determinable` 或 `context_dependent`（生理/环境/营养/药害/根部）；加上下文后由评测脚本自动归为 `with_context` |
| `difficulty` | 枚举 | 是 | `easy` / `medium` / `hard`（模糊、局部、多病并存为 hard） |
| `directMarkerKeys[]` | 数组 | 否 | 画面中明确可见的直接证据标记（提示词【8】闭集），用于以后的规则层 |
| `keyFollowUpTopics[]` | 数组 | 否 | 病史依赖类 1～3 个关键追问项（后期迭代 z8v0kmvh4x 才计分；现在标注，以免日后返工） |
| `labelBasis` | 字符串 | 是 | 标注依据：处理记录编号、说明页描述、病原学名，或两人看图的结论 |
| `annotatorA` / `annotatorB` / `adjudicator` | 字符串 | 是 | 两人独立标注；不一致时第三人裁定；记录各自给出的编号 |
| `agreement` | 枚举 | 是 | `agree` / `adjudicated` / `excluded` |
| `contexts` | 对象 | 见第 3 节 | 无 / 一致 / 中性 / 冲突四种上下文 |
| `split` | 枚举 | 是 | `dev`（开发集）；封存测试集另建，与开发集不重叠 |

## 2. 两人标注流程

1. 标注人 A、B 分别独立看图（不看来源说明，以免被带偏），给出 `primaryCauseCode`、`acceptableCauseCodes`、`directMarkerKeys` 和 `difficulty`。
2. 再对照来源说明或处理记录。看图结论与说明一致的，记 `agree`；不一致的交第三人裁定，记 `adjudicated`；仍无法确定的记 `excluded`，不进入开发集（例如探针第 18 条那种文件名与说明冲突的情况）。
3. 每 50 个案例统计一次 A 与 B 的一致率；一致率低于 80% 时暂停，先统一标注口径。
4. `S1` 受控诱发案例以处理记录为准，看图只用于确认症状已经出现、能被拍到。

## 3. 上下文构造方案

上下文格式严格按 `diagnosis-context-summary/v1`：最多 12 条事实、每条不超过 40 字，只用合同里的闭集事实键，不含坐标、地址和昵称。每个案例准备四种条件，同一张图分别跑，做配对比较。

| 条件 | 适用案例 | 构造规则 |
|---|---|---|
| `none`（无） | 全部 | 所有事实为「未知」，等同临时案例 |
| `consistent`（一致） | 全部 | 按主因的典型病史填写，**不得出现病名或直接结论** |
| `neutral`（中性） | 全部 | 真实可信、但与主因无关的普通病史 |
| `conflicting`（冲突） | **只用于图像证据清楚的案例**（`directMarkerKeys` 非空，或 `difficulty=easy`） | 指向一个常见易混淆病因的病史，用来测试模型会不会被上下文带偏 |

各类的一致上下文要点（只写事实，不写结论）：

| 主因大类 | 一致上下文写什么 | 冲突上下文指向什么 |
|---|---|---|
| 浇水过多、根腐 | 近 14 天浇水频繁、最近一次很近；盆土偏湿；无排水孔或保水基质 | 缺水：浇水稀少、盆土干 |
| 缺水 | 浇水稀少、最近一次很久以前；盆土干 | 积水：浇水频繁、盆土湿 |
| 日灼 | 近 7 天辐射强；南向或西向窗、阳台；最近换到更亮的位置 | 光照不足：北向窗、辐射弱 |
| 冻害、冷害 | 城市气候剖面偏冷；阳台或户外 | 日灼：强辐射 + 南窗 |
| 光照不足 | 北向窗、辐射弱、最近 Lux 读数低 | 浇水过多 |
| 肥害、缺素 | 基质与盆型信息（施肥事件字段尚未上线，暂时只能写「无记录」，并在报告中注明这一局限） | 浇水过多 |
| 虫害、真菌、细菌（图像可判定类） | 普通但合理的养护记录 | 浇水过多或缺水（检验图像证据是否优先） |

构造纪律：

- 两人独立编写、互审，必须符合园艺常识。
- `S1` 受控诱发案例的一致上下文直接来自真实处理记录（实际浇水次数、温度、Lux），中性与冲突版本由人工改写。
- `S2` 授权用户案例如果有当时的档案和养护记录，用真实记录作为一致上下文。
- 上下文按事实键 + 值结构化存放，由评测脚本拼进提示词的可变尾部；评测时 `hasContext=true` 的案例归入「带上下文」组。

## 4. 评测规模与费用预估（供后续报批）

- 200 案例 × 4 种上下文条件 = 800 次调用（冲突组只覆盖部分案例，实际约 700 次）。
- 按第四轮实测单价（qwen3.6-flash 快照，无缓存，约 0.021 元/次）约 15 元；按 qwen3.5-plus（有显式缓存）可能更低。具体以届时 dry-run 估算为准，并按 50 元总预算和单轮报停线报批。
