# 共享请求结果事件与可靠业务审计边界

- 合同版本：`foundation-request-outcome-audit/v1`。
- 归属任务：[`[P2] 共享基础设施实现`](https://app.clickup.com/t/90182453517/z8v0kmr9mk)。
- 上位合同：`http-api/v1` 的固定处理顺序、公开结果脱敏和审计事件要求；本文件只细化链尾事件失败语义，不改写已冻结的 P1 合同。

## 两种记录不可混称

`executeRequestChain` 链尾的 `writeAudit` 只收到 `allowed`、`denied`、`failed` 和可公开错误类型，不含主体、动作、对象与可靠幂等引用。因此它是**脱敏请求结果事件**，用于可观测性，不能充当 `security_audit_records`、领域账本、发布切换审计或可靠事件的唯一事实源。

会改变用户植物、权益、支付或知识发布状态的命令，其必须保留的业务/安全审计事实须由对应应用服务与业务写入**同一 MySQL 事务**；审计事实写入失败则整个命令回滚。链尾事件不得补救已经提交但没有可靠审计的业务写入。拒绝和只读请求没有业务写事务时，链尾事件可用于尽力记录结果，但写入失败必须另发脱敏告警。

## 链尾失败语义

| 已确定的业务结果 | 链尾事件写入失败时 | 脱敏告警 |
|---|---|---|
| 持久化已成功且公开 DTO 已构造 | 保持原成功状态与正文；不得改成 `500`，不得再写一条虚假的 `failed` 事件 | 记录原事件的结果类别，不传入原始异常 |
| 已确定的公开拒绝 | 保持原状态、稳定错误类型和安全中文消息 | 同上 |
| 业务本身发生内部错误 | 保持泛化 `500 INTERNAL_ERROR`，不泄露原始异常 | 同上 |

调用方可注入专用 `reportAuditFailure` 脱敏告警端口；若未注入或告警端口本身失败，共享层须产生不含请求、凭证、SQL、堆栈和原始异常的固定运行时警告。任何告警失败都不得再次改写业务结果。应用层不得把此尽力事件当作支付、身份绑定、额度扣减或发布操作的可靠审计验收证据。

## 验收与未覆盖范围

- `request-chain.spec.ts` 使用真实请求链和可观测假业务边界，先以链尾失败用例在旧控制流上 RED，再验证成功与拒绝均保持原结果，事件只尝试一次且告警收到原结果类别；脱敏告警和运行时警告同时失效的用例也先 RED 后 GREEN，证明最终业务结果不会被再次改写。
- `node-request-chain-handler.spec.ts` 用真实本机 Node HTTP 请求证明已提交成功不会经适配器变成 `500`。
- 这些测试不证明某一业务命令已在真实 MySQL 事务内写入安全审计，也不证明 CloudBase 网关、Pino 告警采集或告警送达；对应业务域与 P5 集成验收必须另行读回。
