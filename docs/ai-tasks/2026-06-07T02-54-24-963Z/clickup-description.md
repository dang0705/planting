背景

当前 `diagnose-http/diagnosis/question/start` 接口响应非常慢，已影响问诊启动体验。

该接口位于问诊链路的入口阶段，用户点击开始问诊后，前端需要尽快拿到当前模式的题包或起始问答数据。如果该接口继续承担过多动态诊断、数据库查询、旧状态机兼容、运行时组装等职责，会导致首屏等待明显变长。

本任务从架构角度优化接口响应速度，前提是：

不启用任何付费功能。
不依赖 Redis、付费缓存、云函数升配、付费 CDN、付费数据库能力等方案。
优先通过职责收敛、静态化、预计算、代码路径裁剪和免费缓存策略优化响应。

目标

优化 `diagnose-http/diagnosis/question/start` 接口响应速度，使其在常规热启动路径下达到 500ms 内响应。

需要明确区分：

热启动 / 常规请求：目标 <= 500ms。
冷启动：尽量优化，但在不开启付费保活、升配等能力前提下，不承诺绝对 <= 500ms。

范围

必须做

梳理 `diagnose-http/diagnosis/question/start` 接口入口与完整调用链。
测量当前接口耗时，区分冷启动、热启动、数据库查询、业务计算、序列化、日志等耗时来源。
梳理该接口当前是否仍经过旧 diagnosis-engine、动态下一题、复杂状态机、数据库读取或不必要的运行时组装。
将 start 接口职责收敛为：根据 mode / route 返回当前模式固定题包或最小启动数据。
黄叶模式等固定题包优先走静态配置或模块级预加载结构，避免每次请求重复查询和重复构建。
移除或绕开 start 接口中不必要的动态诊断逻辑、旧兼容分支、N+1 查询、外部服务调用和重型对象转换。
避免 start 接口调用天气、养护、图片识别、支付、登录等无关模块。
减少响应体字段，只返回前端启动问诊所需的最小数据。
对固定题包建立免费缓存策略，例如：模块级内存缓存、启动时静态常量、构建期生成数据或轻量本地映射。
确保缓存策略不依赖付费服务，并能在云函数实例重启后自动恢复。
补充最小性能验证脚本或手动验证方法，记录优化前后耗时。
确保接口语义不变：不改变 outcome / route 判定权重，不改变数据库发布链路。

不做

不启用 Redis、付费缓存、云函数付费保活、云函数升配、付费 CDN 或其他付费功能。
不重写黄叶 outcome / route 判定权重。
不新增诊断评分系统。
不修改数据库发布链路。
不扩大到养护算法、天气算法、图片识别、支付、登录等无关模块。
不为了性能把所有模式题库无边界全量下发给前端。
不牺牲问诊模式边界：只能返回当前 mode / route 所需题包或启动数据。

建议架构方向

一、先定位慢点

优先在接口关键节点增加临时耗时日志或本地性能埋点：

入口接收请求。
参数解析完成。
mode / route 解析完成。
题包获取完成。
业务适配完成。
响应序列化前。
接口结束。

输出示例：

start.totalMs
start.parseMs
start.resolveModeMs
start.loadPackageMs
start.adaptResponseMs
start.serializeMs

不要长期保留噪音日志，最终只保留必要的性能诊断信息或删除临时日志。

二、收敛 start 接口职责

`/diagnosis/question/start` 不应再承担完整诊断推理。它应尽量退化为：

校验入参。
解析 mode / route。
读取当前模式固定题包。
返回最小启动响应。

理想结构：

getQuestionPackageByMode(mode)

而不是：

resolveDynamicBranch()
getCurrentQuestion()
getNextQuestion()
advanceDiagnosisState()
mergeRuntimeContext()
queryDiagnosisRulesAtRuntime()

三、题包静态化 / 预计算

对于黄叶等固定题包：

优先放在代码内静态配置、JSON 常量或轻量模块映射中。
在云函数实例加载时完成一次性初始化。
请求进来时只做 O(1) 映射读取。
避免每次请求访问数据库组装固定题包。
避免每次请求深拷贝大对象，必要时返回只读结构或轻量 copy。

四、响应体瘦身

接口只返回前端启动问诊必要字段，例如：

mode
route
questions
outcomePolicy 或最小扩展信息
version / packageVersion（如已有必要）

不要返回：

所有模式题库。
调试字段。
旧状态机上下文。
未被前端消费的中间结构。
历史兼容字段。
大段规则说明。

五、免费缓存边界

允许使用：

模块级内存缓存。
静态常量。
构建期生成文件。
轻量本地映射。
无付费依赖的基础云函数运行时缓存。

不允许使用：

Redis。
付费云缓存。
云函数付费保活。
云函数升配作为主要解决方案。
付费 CDN 或边缘函数。

验收标准

`diagnose-http/diagnosis/question/start` 常规热启动响应时间达到 500ms 内。
接口职责清晰，只负责问诊启动所需的 mode / route / 题包返回。
固定题包读取不再依赖重型动态计算路径。
没有启用任何付费能力。
没有引入 Redis、付费缓存、云函数付费保活、升配等方案。
没有修改 outcome / route 判定权重。
没有修改数据库发布链路。
没有引入所有模式题库无边界全量下发。
前端开始问诊流程正常。
lint / 类型检查通过。
任务结果中必须包含优化前后耗时对比。

风险与注意事项

500ms 目标应以常规热启动路径为主。云函数冷启动在免费能力下可能存在不可控波动，不应通过付费保活或升配解决。
本任务重点是架构瘦身，不是盲目加缓存。
如果接口慢点来自旧 diagnosis-engine，应优先删除或绕开旧复杂路径，而不是在旧复杂逻辑外再包一层缓存。
性能优化必须保持问诊业务边界：当前模式题包可以返回，但不能无边界返回所有模式题库。
