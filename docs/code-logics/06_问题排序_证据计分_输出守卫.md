# 06｜route condition、问题排序、证据收敛与输出守卫

更新时间：2026-06-06

## 1. 文档定位

本文件不再描述既有 ranking 计分如何决定追问。当前主链的有效排序与追问由 route planner 的 candidate state、condition result、question priority、requiredForClosure、stepNo 与 maxQuestionCount 决定。

## 2. route 常量

当前 route 模式常量是 `multi_outcome_route`。候选状态包括：

- `candidate`
- `needs_question`
- `strengthened`
- `weakened`
- `display_eligible`
- `closure_eligible`
- `blocked`

condition result 包括：

- `pass`
- `fail`
- `block`
- `need_more_info`
- `conflict`

代码来源：`cloudfunctions/diagnose-http/constants/outcome-route.js` 3-23。

## 3. route evidence context

route planner 不直接吃前端原始文本。它使用 `buildRouteEvidenceContext` 将观察证据、视觉 route symptom keys、answer effects、answered pairs、symptom class keys 等整理为 route 可判断上下文。

这意味着文档不能把“用户选项文本”直接写成 outcome 判定事实；实际有效的是 option mapping / answer effects / route condition 组合。

代码来源：`cloudfunctions/diagnose-http/domain/outcome-route-planner-helpers.js` 145-262。

## 4. 候选 outcome 状态

route planner 对每个 outcome：

1. 找到匹配 routes。
2. 评估 conditions。
3. 判断是否 blocker、是否 pass、是否 need more info。
4. 为缺失 condition 找 candidate questions。
5. 形成 `candidateOutcomeStates`。
6. 收集可见 outcome 与下一步问题。

代码来源：`cloudfunctions/diagnose-http/domain/outcome-route-planner.js` 77-261。

## 5. 问题排序

候选问题排序顺序：

1. `askPriority` 高的优先。
2. `requiredForClosure` 优先。
3. `stepNo` 小的优先。
4. 候选 outcome 原始顺序优先。
5. `questionKey` 字符串排序保守策略。

排序后去重，并按 `maxQuestionCount` 截断。当前常规 route 主链传入 1。

代码来源：`cloudfunctions/diagnose-http/domain/outcome-route-planner.js` 280-303。

## 6. 是否追问

`requiresFollowUp` 只有在以下条件同时满足时为 true：

- `canAskAnotherFollowUpRound` 为 true。
- 存在 `nextQuestionKeys`。
- 存在 required question，或当前没有可见 outcome，或行动建议冲突需要分流。

代码来源：`cloudfunctions/diagnose-http/domain/outcome-route-planner.js` 327-332。

## 7. 是否输出

如果 route 有可见 outcome，主链会生成 `route_visible_outcomes_ready`。如果 route 输出开启但没有可见 outcome，会进入保守 uncertain 分支。最终仍需 stop state 与 output eligibility 通过。

代码来源：`cloudfunctions/diagnose-http/domain/diagnosis-engine.js` 6855-6966；`cloudfunctions/diagnose-http/domain/stop-state/output-eligibility-evaluator.js` 79-117。

## 8. 输出守卫

候选 outcome 不能只因为分数高就公开显示。公开输出依赖 route 可见性和输出资格，而不是既有 ranking top1。

在 output eligibility 层，系统要求：

- `stage === final`
- stop state 已停止
- active package state 为 0
- 有正式 stop decision
- outcome type 正式

代码来源：`cloudfunctions/diagnose-http/domain/stop-state/output-eligibility-evaluator.js` 79-117。

## 9. 黄叶流额外守卫

黄叶 flow 在 route planner 和诊断引擎中有额外 guard：

- 当 symptom class 是 `yellowing_mode` 或 active symptom keys 都属于 yellowing flow，会过滤黄叶护理环境候选 outcome。
- 既有黄叶 flow 问题可被禁用/过滤。
- 当黄叶必需组未完成时，可能 hold route output 或触发黄叶 condition follow-up。

代码来源：`cloudfunctions/diagnose-http/domain/outcome-route-planner.js` 26-39、187-212；`cloudfunctions/diagnose-http/domain/diagnosis-engine.js` 5993-6038。

## 10. 文档禁区

不得把以下内容写成当前事实：

- “ranking score 直接决定最终主输出”。
- “score gap 达标即可停止”。
- “question selector 是当前主问诊模式”。
- “黄叶 4 题可绕过 stop/output 资格直接输出”。
