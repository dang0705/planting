# 05｜问诊系统：问题生成、过滤、停止策略

更新时间：2026-06-06

## 1. 当前问诊事实

当前问诊以 route 模式为唯一主模式。文档不再使用旧“追问池 / 排序分差 / hypothesis pool”作为当前判断依据。

问诊的真实运行对象是：

- `routeDecision.requiresFollowUp`
- `routeDecision.nextQuestionKeys`
- `routeDecision.nextQuestions`
- `followUps`
- `questionQueue`
- `stopState`
- `outputEligibility`

## 2. 问题来源

当前有效问题来源分三类：

### 2.1 route-planned follow-up

常规路径由 `planOutcomeRoutes` 生成 `nextQuestionKeys` 和 `nextQuestions`，再由 `buildRoutePlannedFollowUps` 转为前端可展示问题。

常规路径上限为 1：route planner `maxQuestionCount: 1`，`buildRoutePlannedFollowUps(maxQuestions: 1)`，最终候选追问 `.slice(0, 1)`。

代码来源：`cloudfunctions/diagnose-http/domain/outcome-route-planner.js` 280-332；`cloudfunctions/diagnose-http/domain/diagnosis-engine.js` 6106-6120、6191。

### 2.2 黄叶手动 4 题题包

黄叶手动入口会在 `manual-symptom-question-start-fast-path.js` 中生成四个固定护理上下文维度：

1. 浇水频率上下文。
2. 光照变化上下文。
3. 施肥/生长上下文。
4. 通风/湿度上下文。

当这四题都构造成功时，响应层会返回 `questionPackage`，要求前端以 package 展示和 package 提交。

代码来源：`cloudfunctions/diagnose-http/app/manual-symptom-question-start-fast-path.js` 30-35、132-156、263-319。

### 2.3 retake / 图片补拍分支

图片补拍不是普通文字追问。`preferredRoutePrimaryAction === retake_first` 时会通过响应字段提示前端走图片补充路径。文档不得把 retake 当成普通 `followUps` 文本题。

## 3. 过滤与去重

常规 follow-up 会经过多层过滤：

- 已答问题过滤。
- 禁用黄叶旧问题过滤。
- 黄叶等价维度已答过滤。
- 最终视觉 presence 过滤。
- 已回答 route constraint 过滤。
- `followUpStopPolicy` 检查。

最终只有 `filteredFollowUps` 进入 public response。

代码来源：`cloudfunctions/diagnose-http/domain/diagnosis-engine.js` 6134-6220。

## 4. question queue 的真实作用

`buildRuntimeArtifacts` 会为响应生成 `questionQueue`、`stopState`、`outputEligibility` 与 trace。`questionQueue` 是后续回答归属校验和输出资格的重要条件。

当前关键事实：`planQuestionQueue` 只取 `response.followUps.slice(0, 1)`，因此默认只建立一个 active question item。

代码来源：`cloudfunctions/diagnose-http/domain/runtime-artifacts.js` 81-107；`cloudfunctions/diagnose-http/domain/question-queue/question-queue-planner.js` 89-199。

## 5. 追问持久化与归属校验

`persistRoundRuntime` 在 `followUpRequired` 时调用 `appendFollowUpQuestions`。有效黄叶题包会设置 `allowUnqueuedQuestions: true`，按 package 保留同一当前轮次的 sibling questions；非题包路径继续通过 `filterQuestionsByQuestionQueue(..., { requireQueueAnchor: true })` 按 question queue 锚点过滤问题后再落库。

`validateFollowUpAnswerOwnership` 会从持久化 follow-up 与 question queue 中计算允许回答的问题 key。任何不在 allowed keys 中的回答都会失败。

代码来源：`cloudfunctions/diagnose-http/services/round-runtime-persistence-service.js` 79-87；`cloudfunctions/diagnose-http/services/session-follow-up-service.js` 124-136、346-395；`cloudfunctions/diagnose-http/utils/follow-up-contract.js` 19-47。

## 6. 黄叶 4 题题包的必须表述

必须写成：

> 黄叶手动入口响应、前端展示/提交、后端 follow-up 持久化与 answer ownership 已支持有效 4 题 package；legacy `questionQueue` 仍可锚定首题作为兼容/选择 artifact，但不得拒绝同一 package 当前轮次内的 sibling questions。非 package 路径仍按 queue-anchor 单题语义工作。

不能写成：

> 所有诊断模式都默认支持任意多题套餐提交。

原因：当前只有有效题包路径允许 sibling questions 绕过 queue-anchor 过滤；非题包路径仍受 `planQuestionQueue` 与 `appendFollowUpQuestions` 的单题锚点约束。

## 7. 回答提交规则

`/diagnosis/answer` 的当前规则：

- 必须携带有效 `diagnosisSessionId`。
- 必须能加载 session。
- 当前 round 必须符合 session 状态。
- `answers` 与 `images` 至少有一个，但不能混用成非法请求。
- `answer_revision` 不能带图片。
- 问题 key 与 option key 必须在合法映射中。
- 非 revision 提交通常会 mark follow-up answered 与 question queue answered。

代码来源：`cloudfunctions/diagnose-http/app/diagnosis-answer-runner.js` 77-131、142-253、255-380。

## 8. 停止策略

停止不是“没有问题就停止”的简单判断。停止必须满足 stop state：

- `stage === final`
- `followUpRequired === false`
- question queue 无 active items
- 有正式 outcome type
- 有显式 stop decision
- stop reason 在 final stop reasons 中
- uncertain 有合法理由

代码来源：`cloudfunctions/diagnose-http/domain/stop-state/stop-state-evaluator.js` 6-12、84-158。

## 9. 输出资格

输出资格由 `evaluateOutputEligibility` 判断。即便 stop reason 看起来已经结束，只要 stop state 未停止、queue 仍 active 或缺正式 outcome/stop decision，输出仍应 blocked。

代码来源：`cloudfunctions/diagnose-http/domain/stop-state/output-eligibility-evaluator.js` 79-117。

## 10. 开发检查点

修改问诊时必须检查：

- route planner 是否仍只生成 1 个常规追问。
- 黄叶题包是否仍只在 manual question-start fast path 产生。
- frontend response 是否正确保留 `questionPackage`。
- question queue 与 follow-up 持久化是否和题数协议一致。
- answer ownership 是否允许前端实际提交的答案集合。
- stop state 与 output eligibility 是否仍阻止未完成追问提前输出。
