# 05｜问诊系统：问题生成、过滤、停止策略

更新时间：2026-06-07

## 1. 当前问诊事实

当前诊断以 route 模式为主链，当前问诊题目按 mode question package 工作。文档不再使用旧“追问池 / 排序分差 / hypothesis pool / dynamic next-question helper”作为当前判断依据。

问诊的真实运行对象是：

- `getQuestionPackageByMode(mode)`
- `questionPackage`
- `uiHints.answerSubmitMode`
- `uiHints.questionDisplayMode`
- `questionQueue`
- `stopState`
- `outputEligibility`

## 2. 问题来源

当前有效问题来源分三类：

### 2.1 mode question package

固定题包由 `QUESTION_PACKAGE_BY_MODE` 和 `getQuestionPackageByMode(mode)` 声明。当前 `yellow_leaf` 映射为 4 题 package，`wilting_droop` 映射为 5 题 package；两者都包含固定维度、package 展示/提交模式和 `outcomePolicy`。

代码来源：`cloudfunctions/diagnose-http/app/question-package-response.js` 14-58、61-82；`cloudfunctions/diagnose-http/app/wilting-droop-question-package.js` 5-151。

### 2.2 非 package route 兼容路径

route planner 仍负责证据分流和输出决策。非 package 路径的 queue 保持单题上限；不得把它写成固定题包的题数权威。

代码来源：`cloudfunctions/diagnose-http/domain/diagnosis-engine.js` 2257-2266、3105-3113；`cloudfunctions/diagnose-http/domain/question-queue/question-queue-planner.js` 56-74、109-177。

### 2.3 黄叶静态 4 题题包

黄叶手动入口的 `yellowing_mode` 会先在 `static-question-package-start.js` 中生成四个固定护理上下文维度：

1. 浇水频率上下文。
2. 光照变化上下文。
3. 施肥/生长上下文。
4. 通风/湿度上下文。

当这四题都构造成功时，静态题包启动路径会通过 `getQuestionPackageByMode('yellow_leaf')` 返回 `questions` 与 `questionPackage`，要求前端以 package 展示和 package 提交。默认路径只保存 package snapshot；未配置固定题包的手动模式返回 501，不再转入 route planner。

代码来源：`cloudfunctions/diagnose-http/app/static-question-package-start.js` 82-119、159-233；`cloudfunctions/diagnose-http/app/diagnosis-question-start-runner.js` 211-328；`test-question-start-performance.mjs` 34-68、131-143。

### 2.4 枯萎/发蔫静态 5 题题包

枯萎/发蔫手动入口会在 `static-question-package-start.js` 中生成 `wilting_droop` 固定题包，`sourceMode` 为 `manual_wilting_droop_route_package`，问题顺序为：

1. Q0：过去 10 天浇水行为，`uiVariant/renderMode: care_behavior_timeline`。
2. Q1：发蔫形态。
3. Q2：发蔫节律与环境点位。
4. Q3：最近 7 天应激事件。
5. Q4：茎基部软烂、异味、水渍软烂、黄叶落叶增加、病虫扩散等高危异常。

该题包完成后可产出多个可见行动 outcome，并用冲突动作解释阻断不合适的补水、喷水、施肥、再次换盆、暴晒等动作。

代码来源：`cloudfunctions/diagnose-http/app/wilting-droop-question-package.js` 5-151；`cloudfunctions/diagnose-http/app/static-question-package-start.js` 10-20、147-233；`cloudfunctions/diagnose-http/domain/wilting-droop-outcome-resolver.js` 1-424；`test-wilting-droop-package.mjs` 37-170。

### 2.5 retake / 图片补拍分支

图片补拍不是普通文字问题包。`preferredRoutePrimaryAction === retake_first` 时会通过响应字段提示前端走图片补充路径。文档不得把 retake 当成 package 主路径的文本题。

## 3. 过滤与去重

非 package 兼容路径仍会经过多层过滤：

- 已答问题过滤。
- 禁用黄叶旧问题过滤。
- 黄叶等价维度已答过滤。
- 最终视觉 presence 过滤。
- 已回答 route constraint 过滤。
- `followUpStopPolicy` 检查。

当前 package answer submit 的主路径会终止问诊轮次，`diagnosis-engine.js` 中旧动态 follow-up 生成残留不得作为 active fact 重新写入文档。

代码来源：`cloudfunctions/diagnose-http/domain/diagnosis-engine.js` 3185-3187；`test-question-package.mjs` 348-353。

## 4. question queue 的真实作用

`buildRuntimeArtifacts` 会为响应生成 `questionQueue`、`stopState`、`outputEligibility` 与 trace。`questionQueue` 是兼容运行时结构，但不是固定题包的题数或归属权威。

当前关键事实：package 主响应字段是 `questions`，题包题数来自 `questionPackage.questionCount`；非 package 兼容响应默认只建立 1 个 active question item。

代码来源：`cloudfunctions/diagnose-http/domain/runtime-artifacts.js` 81-107；`cloudfunctions/diagnose-http/domain/question-queue/question-queue-planner.js` 56-74、109-177。

## 5. package snapshot 与归属校验

`persistRoundRuntime` 在静态题包启动路径使用 `questionPackageSnapshotOnly`，把 `response.questions` 写入 `runtimeSnapshot.questionPackageSnapshot.packageQuestions`，并跳过 legacy question rows。

package answer ownership 读取 `questionPackageSnapshot.packageQuestions` 计算允许回答的问题 key。任何不在 allowed keys 中的回答都会失败。非 package 兼容路径才继续使用 legacy question rows 与 queue anchor。

代码来源：`cloudfunctions/diagnose-http/services/round-runtime-persistence-service.js` 17-35、67-128；`cloudfunctions/diagnose-http/app/package-answer-ownership-runtime.js` 11-24、75-90；`cloudfunctions/diagnose-http/app/diagnosis-answer-runner.js` 153-202。

## 6. 黄叶 4 题题包的必须表述

必须写成：

> 黄叶手动入口响应、前端展示/提交、package snapshot 与 answer ownership 已支持有效 4 题 package；`questionQueue` 是运行时兼容/校验结构，不得作为 package sibling questions 的归属权威。非 package 路径仍按 queue-anchor 单题语义工作。

不能写成：

> 所有诊断模式都默认支持任意多题套餐提交。

原因：当前只有有效题包路径按 `questionPackageSnapshot.packageQuestions` 校验包内题；非题包路径仍受 legacy rows 与 queue anchor 的单题锚点约束。

## 7. 回答提交规则

`/diagnosis/answer` 的当前规则：

- 必须携带有效 `diagnosisSessionId`。
- 必须能加载 session。
- 当前 round 必须符合 session 状态。
- `answers` 与 `images` 至少有一个，但不能混用成非法请求。
- `answer_revision` 不能带图片。
- 问题 key 与 option key 必须在合法映射中。
- 非 revision 的 package 提交会用 snapshot 构造本轮 answered runtime；非 package 兼容提交才继续标记 legacy question rows 与 question queue。

代码来源：`cloudfunctions/diagnose-http/app/diagnosis-answer-runner.js` 77-131、142-253、255-380。

## 8. 停止策略

停止不是“没有问题就停止”的简单判断。停止必须满足 stop state：

- `stage === final`
- question queue 无 active items
- 有正式 outcome type
- 有显式 stop decision
- stop reason 在 final stop reasons 中
- uncertain 有合法理由

代码来源：`cloudfunctions/diagnose-http/domain/stop-state/stop-state-evaluator.js` 6-12、84-158。

## 9. 输出资格

输出资格由 `evaluateOutputEligibility` 判断。即便 stop reason 看起来已经结束，只要 stop state 未停止、queue 仍 active 或缺正式 outcome/stop decision，输出仍应 blocked。

代码来源：`cloudfunctions/diagnose-http/domain/stop-state/output-eligibility-evaluator.js` 79-117。

## 10. 开发检查点

修改问诊时必须检查：

- `getQuestionPackageByMode(mode)` 是否仍是固定题包入口。
- 黄叶题包是否仍映射为 4 题 package 并带有 `outcomePolicy`。
- 枯萎/发蔫题包是否仍映射为 `wilting_droop` 5 题 package、`sourceMode: manual_wilting_droop_route_package`，且 Q0 仍是 `care_behavior_timeline`。
- frontend response 是否正确保留 `questionPackage`。
- package snapshot 是否包含前端实际收到的 `questions`。
- answer ownership 是否基于 `questionPackageSnapshot.packageQuestions` 允许前端实际提交的答案集合。
- stop state 与 output eligibility 是否仍阻止未完成追问提前输出。
