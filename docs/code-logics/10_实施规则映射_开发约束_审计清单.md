## 2. 问诊改动审计清单

修改问诊前后必须检查：

- [ ] 是否仍明确当前唯一主问诊模式是 route 模式。
- [ ] 是否没有恢复既有 ranking / score-gap 作为追问或停止依据。
- [ ] 是否没有把既有 dynamic next-question helpers / active follow-up residues 写回当前事实。
- [ ] 固定题包是否通过 `getQuestionPackageByMode(mode)` 进入。
- [ ] 若引入题包，`/diagnosis/question/start` 是否返回 active `questions`，而不是既有数组字段。
- [ ] 若引入题包，`runtimeSnapshot.questionPackageSnapshot.packageQuestions` 是否覆盖包内所有问题。
- [ ] 若引入题包，answer ownership 是否基于 package snapshot 覆盖包内所有问题。
- [ ] 黄叶 4 题是否仍优先在 `static-question-package-start.js` 的模块级静态题包启动路径中产生。
- [ ] `yellowing_mode` 静态题包启动路径是否仍不加载 prior repository、manual fast path 或 `diagnosis-engine`，且默认路径仍通过 `persistRoundRuntime(..., { questionPackageSnapshotOnly: true })` 保存 snapshot。
- [ ] 黄叶题包是否仍带有 `outcomePolicy`。
- [ ] 黄叶与枯萎发蔫共享浇水频率题是否仍由 `cloudfunctions/diagnose-http/app/diagnosis-question-registry.js` 只映射 packageTopic 到 DB questionKey，`questionKey` 是否为 `q_observed_probe__leaf_yellowing__watering_frequency_context`。
- [ ] 共享浇水频率题的题干、帮助文案、选项和 UI 元数据是否仍来自 `question_library_v5_real` / `question_option_mapping_v5_real`，而不是后端临时硬编码或生成。
- [ ] 题包响应中的题目身份是否仍只依赖 `questionKey`，后端是否没有为了兼容临时生成或补出 `questionId`。
- [ ] `wilting_droop` 是否仍是 5 题固定 package，`sourceMode` 是否仍是 `manual_wilting_droop_route_package`。
- [ ] `wilting_droop` Q0 是否仍使用 `CareBehaviorTimeline` / `care_behavior_timeline`，Q1-Q4 是否仍覆盖发蔫形态、节律/环境、近期应激和高危异常。
- [ ] `wilting_droop` 终端结果是否仍输出“建议行动清单”、多个 `visibleOutcomes`、冲突动作解释、高危提醒和观察周期。
- [ ] `wilting_droop` 是否没有引入 ranking、score、probability、main-cause 或“最可能原因”排序口径。
- [ ] `questionPackage` 与 `uiHints` 是否仍能被前端 normalizer 保留。
- [ ] 前端是否按 package 模式整包展示和提交。
- [ ] `/diagnosis/answer` 是否能校验包内所有问题 key 与 option key。

## 3. 停止与输出资格审计清单

- [ ] 文档是否明确 stop state 才是停止事实。
- [ ] 文档是否明确 output eligibility 才是输出资格事实。
- [ ] 是否没有把“无 active questions”简化成“一定可输出”。
- [ ] 是否没有把“答完 4 题”简化成“一定可输出”。
- [ ] route 无可见 outcome 时是否仍走保守 uncertain。
- [ ] uncertain 输出是否有合法理由。
- [ ] pending package question 未清空时是否阻止输出。

## 4. HTTP 接口审计清单

- [ ] `/diagnosis/question/start` 是否仍直接 `buildFrontendResponse`。
- [ ] `/diagnosis/start` 与 `/diagnosis/answer` 是否仍经过 presenter。
- [ ] 文档是否保留这三个入口的差异。
- [ ] 前端是否没有假设三个入口响应路径完全一致。

## 5. 文档禁用表述

以下表述不得作为当前事实出现：

- “问诊由 ranking 分数差控制”。
- “score gap 达标即可停止”。
- “固定答满 N 题即可输出”。
- “questionPackageSnapshot 是固定题包的题数权威”。
- “既有数组字段是 package 主响应字段”。
- “`/diagnosis/question/start` 未命中固定题包时转入 `diagnosis-engine`”。
- “package answer ownership 以 session follow-up rows 为主”。
- “question-start 与 start/answer 的 presenter 行为一致”。
- “`wilting_droop` 结果页是最可能原因 / 主因排序 / 概率排序”。
- “既有 Sxx all-in-one 是最新结构源”。

## 6. 允许保留的历史概念

既有 selector、既有 ranking、既有 Sxx 规则可以作为历史背景存在，但必须标记为：

- deprecated
- historical
- not current runtime source
- do not use for implementation

不得将它们放在 Facts 层。

## 7. Codex / AI 执行规则

AI 执行任务时：

1. 先看代码，后看文档。
2. 文档只用于加速定位，不作为反驳代码的证据。
3. 发现文档和代码冲突时，必须改文档。
4. 改 `new-rules` 后，才能改 `ai_and_memories` 的引用行号和章节。
5. 不能引用过时行号、过时章节或过时概念。
6. 对跨层不一致必须明说，不能为保持文档好看而隐藏。

## 8. 本轮已确认的高风险边界

黄叶 4 题题包当前是固定 package 协议事实：响应、前端展示/提交、package snapshot 与归属校验都必须允许包内 4 题。枯萎/发蔫 5 题题包当前是另一个固定 package 协议事实，结果页以“建议行动清单”和多 `visibleOutcomes` 为中心。高风险边界是不要把非 package 的单题 session question row anchor 语义外推到 package，不要把 package 语义外推到所有诊断模式，也不要把行动清单改写成 ranking / score / probability / main-cause。
