# 03｜诊断运行时主链路：route-only 执行逻辑

更新时间：2026-06-07

## 1. 当前主链结论

当前诊断主链以 route 模式汇总证据和决定输出；当前问诊入口按 mode question package 收敛。文档中的旧 ranking、score gap、多候选逐题追问、旧 dynamic next-question helpers、固定题数停止等概念，不再作为当前实现事实。

主链的核心闭环是：

1. 收集图片、手动症状、历史回答、answer effects、视觉 route hints。
2. 构造 `routeEvidenceContext`。
3. 调用 `planOutcomeRoutes`。
4. route planner 评估 route groups、routes、gates、route questions。
5. 若进入固定题包，使用 `getQuestionPackageByMode(mode)` 构造 package 响应和 package ui hints；当前明确包含 `yellow_leaf` 4 题与 `wilting_droop` 5 题。
6. package answer submit 作为当前问诊轮次终止态传入诊断引擎；非 package 兼容路径保持单题 queue-anchor 语义。
7. 构造 public response，再生成 runtime artifacts：question queue、stop state、output eligibility、diagnostic trace。

## 2. route planner 的输入与输出

`planOutcomeRoutes` 接收候选 outcome、route evidence context、是否可追问、最大可见 outcome 数、最大问题数和 feature flags。

当前常规 route 调用仍传入 `maxQuestionCount: 1`，但这不是当前题包权威。固定题包由 `QUESTION_PACKAGE_BY_MODE` 和 `getQuestionPackageByMode(mode)` 明确声明；非 package 路径才保持单题 queue-anchor 行为。

代码来源：`cloudfunctions/diagnose-http/domain/outcome-route-planner.js` 41-49；`cloudfunctions/diagnose-http/domain/diagnosis-engine.js` 2257-2266、3105-3113；`cloudfunctions/diagnose-http/app/question-package-response.js` 5-82；`cloudfunctions/diagnose-http/app/wilting-droop-question-package.js` 5-151。

## 3. route decision 的状态机

每个候选 outcome 会根据 route gate 进入以下状态之一：

- `blocked`：存在阻断且没有通过 route。
- `needs_question`：需要更多信息且未被阻断。
- `display_eligible`：已有通过 route，可进入可见 outcome。
- `candidate`：仍是候选，但未满足展示或追问条件。

route planner 会把可问问题排序、去重并按 `maxQuestionCount` 截断，再根据必要问题、可见 outcome 数和行动冲突决定是否还需要问题。

代码来源：`cloudfunctions/diagnose-http/domain/outcome-route-planner.js` 187-224、280-332。

## 4. 旧动态追问逻辑的当前状态

当前 `diagnosis-engine.js` 不再保留旧动态问诊 selector / next-question helper 作为活动实现。不得把 `getNextQuestion`、`resolveDynamicBranch`、`advanceDiagnosisState`、`mergeQuestionRuntimeContext` 或旧动态问诊残留写成当前问诊权威。

当前保留的事实是：

- route planner 仍服务于证据分流和输出决策。
- 非 package 路径的 queue 默认单题。
- package 路径由 question package 元数据决定题数，不能回退成旧动态追问。

代码来源：`cloudfunctions/diagnose-http/domain/diagnosis-engine.js` 2257-2266、3105-3113、3185-3187；`test-question-package.mjs` 348-353。

## 5. 静态题包启动路径

当 `/diagnosis/question/start` 的手动模式解析为 `yellowing_mode` 时，系统固定进入 `static-question-package-start.js` 的模块级静态题包启动路径。该路径用 `getQuestionPackageByMode('yellow_leaf')` 的目标维度生成 4 个护理上下文问题，并直接返回：

- `stage: question_package`
- `status: active`
- `routePrimaryAction: ask_first`
- `stopReason: await_package_answers`
- `sessionStatus: awaiting_package_answers`
- active `questions`
- `questionPackage.mode: yellow_leaf`
- `questionPackage.sourceMode: manual_yellowing_care_environment_frontloaded`
- `questionPackage.questionCount: 4`
- `answerSubmitMode: package`
- `questionDisplayMode: package`
- `fixedQuestionPackage: true`
- `outcomePolicy.allowMultipleOutcomes: true`
- `outcomePolicy.preferSingleOutcome: false`

当手动模式命中枯萎/发蔫时，同一静态题包启动路径返回 `wilting_droop` 5 题 package：

- `questionPackage.mode: wilting_droop`
- `questionPackage.sourceMode: manual_wilting_droop_route_package`
- `questionPackage.questionCount: 5`
- Q0 `uiVariant/renderMode: care_behavior_timeline`，用于收集过去 10 天浇水行为。
- Q1-Q4 分别收集发蔫形态、节律/环境、近期应激和高危异常。
- `outcomePolicy.allowMultipleOutcomes: true`
- `outcomePolicy.preferSingleOutcome: false`

默认路径通过 `persistRoundRuntime(..., { questionPackageSnapshotOnly: true })` 保存这一轮的 `questionPackageSnapshot`；静态构造不加载 prior repository、manual fast path 或 `diagnosis-engine`。当前未配置固定题包的手动模式返回 501，不再把 start 主路径转入 `runDiagnosisRound`。

代码来源：`cloudfunctions/diagnose-http/app/diagnosis-question-start-runner.js` 3-20、148-170、211-259、261-328；`cloudfunctions/diagnose-http/app/static-question-package-start.js` 82-119、159-233；`cloudfunctions/diagnose-http/app/question-package-response.js` 14-58、61-82；`cloudfunctions/diagnose-http/app/wilting-droop-question-package.js` 5-151；`test-question-start-performance.mjs` 34-68、131-143；`test-wilting-droop-package.mjs` 37-81。

## 6. 黄叶题包的 snapshot 与 ownership 边界

黄叶 4 题题包是当前代码事实，并且有效 `yellow_leaf` package 已按包级 snapshot 与归属校验处理。

已成立的事实：

- 响应包含 4 个 active `questions`。
- `questionPackage` 与 `uiHints` 会告诉前端这是 4 题 package。
- 前端以 package 模式展示题目，并在完成后一次性提交整包答案。
- `persistRoundRuntime` 在静态题包启动路径保存 `runtimeSnapshot.questionPackageSnapshot.packageQuestions`。
- package answer ownership 直接读取 `questionPackageSnapshot.packageQuestions` 生成允许回答的问题 key。

仍需保留的边界：

- 固定题包的题数、归属和停止输入以 `questionPackage`、package snapshot 与整包 answers 为准。
- 非题包路径不得反向约束黄叶 4 题题包。

`CareBehaviorTimeline.vue` 提交的是包内浇水题的虚拟答案 `care_behavior_timeline`，该答案必须在 answer runtime 中保留为合法 option，并在 route 运行前根据 `careBehaviorTimeline` / `environmentCareContext.outputs.wateringContext` 转换成 route 可识别的浇水 option。黄叶整包完成后，以下强阳性必须产生确定 visible outcome，不得落入 conservative uncertain：

- 过浇行为：`care_behavior_timeline` 解析为 `likely_too_wet` 后进入 `often_wet`，输出 `overwatering_root_pressure`。
- 施浓肥 / 近期换盆：`recent_heavy_fertilizer_or_repot` 输出 `fertilizer_repot_stress`。
- 直晒 / 光照突然增强：`stronger_direct_light` 输出 `sunburn`。

代码来源：`cloudfunctions/diagnose-http/services/round-runtime-persistence-service.js` 17-35、54-128；`cloudfunctions/diagnose-http/app/package-answer-ownership-runtime.js` 1-87、90-160；`cloudfunctions/diagnose-http/app/care-behavior-payload.js` 1-129；`cloudfunctions/diagnose-http/app/diagnosis-answer-runner.js` 153-202、273-284、340-381；`test-yellowing-package-outcome-contract.mjs` 1-261。

## 7. 停止决策

`wilting_droop` 整包提交完成后可由 `resolveWiltingDroopOutcomeResult` 直接产出 closed/final 结果。该结果使用 `stopReason: wilting_droop_package_completed`、`outcomeMode: visible_outcomes` 和 `finalResult.problemName/displayName: 建议行动清单`，并保留多个 `visibleOutcomes`、`blockedActionExplanations`、`highRiskWarning`、`observationPeriod`。该路径不得写成 ranking、score、probability、main cause 或“最可能原因”排序。

固定题包阶段不是 final。只有后续 route 运行进入 `final`，才会生成 route stop decision：

- route 有可见 outcome：`route_visible_outcomes_ready`。
- route 无可见 outcome 但仍在 route 模式：输出保守 uncertain。
- 非 route 路径只保留在代码分支中，不应作为当前主事实叙述。

代码来源：`cloudfunctions/diagnose-http/domain/diagnosis-engine.js` 6855-6966；`cloudfunctions/diagnose-http/domain/wilting-droop-outcome-resolver.js` 284-424；`test-wilting-droop-package.mjs` 84-170。

## 8. 输出资格

输出资格不是由题数决定，而是由 runtime artifacts 中的 stop state 与 output eligibility 决定。

`evaluateStopState` 的 final 判定要求：

- `stage === final`
- 无 active question queue
- outcome type 是 `problematic` / `non_problematic` / `uncertain`
- 有显式 stop decision
- stop reason 属于 final stop reasons
- uncertain 必须有合法不确定理由

`evaluateOutputEligibility` 还要求 stop state 已停止、无 active queue、正式 outcome 与正式 stop decision。

代码来源：`cloudfunctions/diagnose-http/domain/stop-state/stop-state-evaluator.js` 6-12、84-158；`cloudfunctions/diagnose-http/domain/stop-state/output-eligibility-evaluator.js` 79-117。

## 9. 文档修正原则

若看到以下写法，必须改：

- “追问由 ranking 分差决定”。应改为 route gate / route decision。
- “答完 N 题即可输出”。应改为 stop state + output eligibility。
- “questionQueue 是黄叶题包题数权威”。应改为 `questionPackage.questionCount` 决定 package `questions` 上限，非 package 才默认单题。
- “question-start 与 start/answer 响应路径等价”。应改为 question-start 直接 `buildFrontendResponse`，start/answer 经 presenter。
