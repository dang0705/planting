# 03｜诊断运行时主链路：route-only 执行逻辑

更新时间：2026-06-06

## 1. 当前主链结论

当前诊断主链已经以 route 模式为唯一问诊主模式。文档中的旧 ranking、score gap、多候选逐题追问、固定题数停止等概念，不再作为当前实现事实。

主链的核心闭环是：

1. 收集图片、手动症状、历史回答、answer effects、视觉 route hints。
2. 构造 `routeEvidenceContext`。
3. 调用 `planOutcomeRoutes`。
4. route planner 评估 route groups、routes、gates、route questions。
5. 若需要继续分流，返回 `requiresFollowUp` 与 `nextQuestionKeys`。
6. 若无需继续分流，形成 route-backed output 或保守 uncertain。
7. 构造 public response，再生成 runtime artifacts：question queue、stop state、output eligibility、diagnostic trace。

## 2. route planner 的输入与输出

`planOutcomeRoutes` 接收候选 outcome、route evidence context、是否可追问、最大可见 outcome 数、最大问题数和 feature flags。

当前常规调用传入 `maxQuestionCount: 1`。因此常规 route 追问不能被写成“一轮多题套餐”。一轮多题只适用于黄叶手动 fast path 的特殊题包响应。

代码来源：`cloudfunctions/diagnose-http/domain/outcome-route-planner.js` 41-49；`cloudfunctions/diagnose-http/domain/diagnosis-engine.js` 5876-5885。

## 3. route decision 的状态机

每个候选 outcome 会根据 route gate 进入以下状态之一：

- `blocked`：存在阻断且没有通过 route。
- `needs_question`：需要更多信息且未被阻断。
- `display_eligible`：已有通过 route，可进入可见 outcome。
- `candidate`：仍是候选，但未满足展示或追问条件。

route planner 会把可问问题排序、去重并按 `maxQuestionCount` 截断，再根据必要问题、可见 outcome 数和行动冲突决定 `requiresFollowUp`。

代码来源：`cloudfunctions/diagnose-http/domain/outcome-route-planner.js` 187-224、280-332。

## 4. 常规追问生成

在 `diagnosis-engine.js` 的完整路径中：

- route planner 以 `maxQuestionCount: 1` 运行。
- `legacyFollowUpAllowed = false`，旧 follow-up selector 不再作为当前事实源。
- route planned follow-ups 使用 `maxQuestions: 1`。
- 最终候选追问再次 `.slice(0, 1)`。

代码来源：`cloudfunctions/diagnose-http/domain/diagnosis-engine.js` 5876-5897、6106-6120、6191-6220。

## 5. 黄叶手动 fast path

当手动模式进入黄叶路径，并且 `buildManualYellowingCareStartFollowUps` 成功生成 4 个护理上下文问题时，系统直接返回：

- `stage: followup`
- `status: active`
- `followUpRequired: true`
- `routePrimaryAction: ask_first`
- `stopReason: await_follow_up`
- `sessionStatus: awaiting_follow_up`
- `questionPackage.mode: yellow_leaf`
- `questionPackage.sourceMode: manual_yellowing_care_environment_frontloaded`
- `questionPackage.questionCount: 4`
- `answerSubmitMode: package`
- `questionDisplayMode: package`

代码来源：`cloudfunctions/diagnose-http/app/manual-symptom-question-start-fast-path.js` 30-35、132-193、231-328。

## 6. 黄叶题包的持久化边界

黄叶 4 题题包是当前代码事实，并且有效 `yellow_leaf` package 已按包级持久化与归属校验处理。

已成立的事实：

- 响应可包含 4 个 `followUps`。
- `questionPackage` 与 `uiHints` 会告诉前端这是 4 题 package。
- 前端 normalizer 会按 `questionCount` 保留多个 follow-up。
- 前端 follow-up 页支持一题一屏展示，最后一次性提交整包答案。
- `persistRoundRuntime` 识别有效黄叶题包后，调用 `appendFollowUpQuestions(..., { allowUnqueuedQuestions: true })`，包内 sibling questions 不再被单题 `questionQueue` 锚点过滤掉。
- `appendFollowUpQuestions` 在 package 持久化路径会保留同一当前轮次的包内问题；非 package 路径仍要求 queue anchor。
- `validateFollowUpAnswerOwnership` 会把同一 answer round 中已持久化且未 answered 的 follow-up rows 加入 allowed keys，因此包内 4 个答案可以一起通过归属校验。

仍需保留的边界：

- `planQuestionQueue` 当前只取 `response.followUps.slice(0, 1)`。
- 这个 legacy queue 仍可作为兼容/选择锚点，但不能拒绝同一有效黄叶题包内的 sibling questions。
- 非题包路径仍保持旧 queue-anchor 单题持久化和归属校验语义。

代码来源：`cloudfunctions/diagnose-http/services/round-runtime-persistence-service.js` 79-87；`cloudfunctions/diagnose-http/services/session-follow-up-service.js` 124-136、346-395。

## 7. 停止决策

若 `followUpRequired` 为 true，`stopDecision` 为 null，stage 是 `followup`。若无需追问，stage 才会变成 `final`，并生成 route stop decision：

- route 有可见 outcome：`route_visible_outcomes_ready`。
- route 无可见 outcome 但仍在 route 模式：输出保守 uncertain。
- 非 route 路径只保留在代码分支中，不应作为当前主事实叙述。

代码来源：`cloudfunctions/diagnose-http/domain/diagnosis-engine.js` 6855-6966。

## 8. 输出资格

输出资格不是由题数决定，而是由 runtime artifacts 中的 stop state 与 output eligibility 决定。

`evaluateStopState` 要求：

- `stage === final`
- `followUpRequired === false`
- 无 active question queue
- outcome type 是 `problematic` / `non_problematic` / `uncertain`
- 有显式 stop decision
- stop reason 属于 final stop reasons
- uncertain 必须有合法不确定理由

`evaluateOutputEligibility` 还要求 stop state 已停止、无 active queue、正式 outcome 与正式 stop decision。

代码来源：`cloudfunctions/diagnose-http/domain/stop-state/stop-state-evaluator.js` 6-12、84-158；`cloudfunctions/diagnose-http/domain/stop-state/output-eligibility-evaluator.js` 79-117。

## 9. 文档修正原则

若看到以下写法，必须改：

- “追问由 ranking 分差决定”。应改为 route gate / route decision。
- “答完 N 题即可输出”。应改为 stop state + output eligibility。
- “黄叶四题已经后端全链路包级化”。应改为响应/前端支持，queue/持久化校验仍有首题锚定边界。
- “question-start 与 start/answer 响应路径等价”。应改为 question-start 直接 `buildFrontendResponse`，start/answer 经 presenter。
