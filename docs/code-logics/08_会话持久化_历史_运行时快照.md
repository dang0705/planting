# 08｜会话持久化、历史与运行时快照

更新时间：2026-06-06

## 1. 文档口径

本文件按当前 route 模式代码事实整理。会话持久化不是“把前端看到的内容保存一份”这么简单；它直接影响下一轮 `/diagnosis/answer` 是否能通过归属校验、旧题是否会被重复提交、最终结果是否能被历史与 review 读取。

## 2. 主要服务文件

| 文件 | 职责 |
|---|---|
| `services/session-service.js` | 会话主服务，构建 session、读取状态、保存历史、反馈、答案标记等 |
| `services/session-read-service.js` | 会话读取 |
| `services/session-runtime-write-service.js` | 运行时写入 |
| `services/session-state-write-service.js` | 会话状态写入 |
| `services/session-finalization-service.js` | 会话最终化 |
| `services/session-follow-up-service.js` | follow-up 持久化、答案标记、归属校验 |
| `services/session-runtime-snapshot-codec.js` | 运行时快照编码/解码 |
| `services/round-runtime-persistence-service.js` | 每轮运行时持久化 |
| `services/question-queue-runtime-service.js` | question queue 状态管理 |
| `services/session-supervision-service.js` | 会话监督与异常状态处理 |

## 3. 会话核心状态

会话至少需要保存：

- 用户 openid。
- `sessionId`。
- 当前轮次与阶段。
- 植物上下文。
- 最近视觉批次 ID。
- observed evidence / derived evidence。
- 已问问题与已回答问题。
- route decision 摘要。
- 当前 follow-up 与 question queue。
- stop state 与 output eligibility。
- 最终结果 ID。

手动症状模式由 `/diagnosis/question/start` 创建会话，初始证据必须保留 `sourceType=manual_symptom_mode`。该路径不得伪造成视觉证据。

## 4. route runtime snapshot

route 模式接管后，运行时快照必须保留可复盘的 route 主链：

- `routeDecision`。
- 候选 outcome 状态。
- `visibleOutcomeKeys` / `visibleOutcomes`。
- `decisionCause`。
- 当前 follow-up 状态。
- stop/output 资格。

这些字段用于 review、历史详情、云端 smoke 和后续治理，不应只存在一次性响应中。

## 5. question queue 与 follow-up 持久化

当前 `questionQueue` 是回答归属校验和输出资格的重要状态。`planQuestionQueue` 会基于当前响应生成 active item；package 响应按 `questionPackage.questionCount` 保留包内全部问题，非题包路径默认单题。非题包路径中 `appendFollowUpQuestions` 会按 queue anchor 过滤后落库；有效黄叶题包路径会允许同一当前轮次的 package sibling questions 一起落库。`validateFollowUpAnswerOwnership` 会用持久化 follow-up 与 queue keys 判断提交是否合法。

代码事实：当前 `planQuestionQueue` 会先识别 package 响应；有 package 时按声明题数保留问题，无 package 时才回到单题上限。这意味着黄叶 4 题题包的 queue、persistence、ownership 都按 package 边界处理；非 package 路径仍按 queue-anchor 单题语义工作。

## 6. 黄叶 4 题题包持久化边界

黄叶手动入口响应、前端展示/提交和后端持久化链路支持有效 4 题 package：

- package queue 保留包内全部问题。
- package persistence 会跳过 queue-anchor 过滤，让包内 sibling questions 在同一当前轮次落库。
- answer ownership 依赖同轮持久化 follow-up rows 与 queue keys，因此已落库的包内 4 题可全量通过。

因此本文件必须区分 package 与非 package：有效黄叶题包可整包持久化与校验；非题包路径仍按 queue-anchor 单题语义工作。

## 7. 答案版本

`prepareAnswerRevision()` 与 `resolveNextAnswerRevision()` 用于推进答案版本，区分同一会话中的多次提交，避免重复提交覆盖状态，并支持审计“第几版答案导致本轮变化”。

`answer_revision` 不能携带图片。普通 answer submit 会标记 follow-up 与 queue answered，并重跑诊断。

## 8. final snapshot 与历史读取

最终结果、`visibleOutcomes`、action advice 与 route decision cause 必须能被 `/diagnosis/result`、历史详情和 review/detail 读取。旧 `primaryOutcome` / `secondaryOutcomes` 只能作为历史兼容来源，不是当前公开出口。

## 9. 同步与异步边界

不能为了性能把下一轮 answer 所需的状态移到无协议后台补写。必须同步完成或可立即恢复的内容包括：

- `diagnosis_sessions.runtime_snapshot_json` 中的 route / follow-up / session 状态。
- 当前有效 follow-up 落库状态。
- 当前答案 mark / answer row 状态。
- final snapshot。

可降级为后台补写的内容只能是 review、审计、兜底恢复或可解释性用途；不得成为下一轮 answer 是否能继续的唯一状态来源。

## 10. 维护要求

新增运行时关键字段时，同步快照编码/解码；新增 follow-up 状态时，同步 question queue、follow-up 持久化和答案校验；新增输出字段时，同步历史详情读取；删除字段必须保留兼容读取逻辑。
