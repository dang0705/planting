# 07｜结果格式化、公开响应与前端接入契约

更新时间：2026-06-07

## 1. 公开响应原则

公开响应必须按 route 与 runtime artifacts 的结果呈现。前端不能自行根据题数、候选列表或旧 ranking 字段判断是否最终输出。

## 2. 前端响应构造

`buildFrontendDiagnosisResponse` 的关键规则：

- 问题来源通过 `resolveResponseQuestions(publicResponse)` 获取，只读取 `questions`。
- 若构造出 `questionPackage`，保留 `questionPackage.questionCount` 个 `questions`。
- 若没有题包，则只保留 1 个兼容问题。
- package 响应中透出 `questions`、`questionPackage` 和 `uiHints`。

代码来源：`cloudfunctions/diagnose-http/app/frontend-response.js` 341-390；`cloudfunctions/diagnose-http/app/question-package-response.js` 5-82。

`/diagnosis/answer` 的终态结果使用 `buildFrontendAnswerResponse`，不再返回完整 round/presenter 大对象：

- 有 active questions 时仍回到 `buildFrontendDiagnosisResponse`。
- final 结果只保留结果页必要字段：`diagnosisSessionId`、`resultId`、`roundId`、`plantId`、`stage`、`status`、`outcomeType`、`stopReason`、`finalResult`、`visibleOutcomes`、`outcomeMode`、`confidenceLevel`、`hasActiveQuestions: false`、`questions: []`，以及存在值时的 plant / non-problematic / human-review 标记。
- `finalResult` 只保留身份、显示名、摘要、严重度、置信度和 outcome type。
- 当 `visibleOutcomes` 非空时，前端建议展示必须从每个 outcome 的 `actionAdviceItems` / `avoidAdviceItems` 读取；answer 响应不再额外返回顶层 `actionAdvice`、`nextSteps`、`whatToAvoid`、`treatmentText`、`preventionText`、`summaryCard`。
- 不返回 `visualBatchTrace`、`visualAggregateSummary`、`outputEligibility`、`routeDecisionCause`、`environmentCareContext` 等结果页不需要的大字段。

代码来源：`cloudfunctions/diagnose-http/handlers/diagnosis-handlers.js` 118-150；`cloudfunctions/diagnose-http/app/frontend-response.js` 491-564。

## 3. 固定题包响应契约

固定题包通过 `getQuestionPackageByMode(mode)` 构造。当前 `yellow_leaf` package 只有在以下条件同时满足时进入前端 package 响应：

- `mode === yellow_leaf`
- `sourceMode === manual_yellowing_care_environment_frontloaded`
- 问题数正好是 4

构造出的题包包含：

- `mode`
- `sourceMode`
- `questionCount`
- `answerSubmitMode: package`
- `questionDisplayMode: package`
- `fixedQuestionPackage: true`
- `outcomePolicy`

代码来源：`cloudfunctions/diagnose-http/app/question-package-response.js` 14-33、61-82、167-173。

当前 `wilting_droop` package 的前端响应条件是：

- `mode === wilting_droop`
- `sourceMode === manual_wilting_droop_route_package`
- 问题数正好是 5
- Q0 使用 `care_behavior_timeline`

构造出的题包同样包含 `answerSubmitMode: package`、`questionDisplayMode: package`、`fixedQuestionPackage: true` 和允许多 outcome 的 `outcomePolicy`。

代码来源：`cloudfunctions/diagnose-http/app/question-package-response.js` 14-58、61-82、167-173；`cloudfunctions/diagnose-http/app/wilting-droop-question-package.js` 5-151；`test-wilting-droop-package.mjs` 37-81。

## 4. 前端 normalizer

前端 normalizer 会：

- 读取 `rawQuestionPackage`。
- 用 `questionPackage.questionCount` 决定 package `questions` 归一化上限。
- 保留 `questionPackage`。
- 保留 `uiHints.maxQuestionsThisRound`、`questionDisplayMode`、`answerSubmitMode`。

代码来源：`src/utils/diagnose-result-normalizer.js` 100-111、216-218、261-267。

## 5. 前端题包页面

前端加载初始结果后，以响应中的 `questions` 作为题包问题栈。

`question-flow.js` 会通过 `isPackageResult` 判断是否题包模式。在题包模式下：

- 用当前题索引控制展示题。
- 最后一题前显示“下一题”，最后一题显示“完成问诊”。
- package 最后一题要求所有题已回答。
- package 模式提交整个题包问题栈。
- 请求模式强制为 `answer_submit`。

黄叶题包与枯萎/发蔫题包的第一题都使用 `CareBehaviorTimeline.vue`。前端提交该题时，answer 中保留虚拟 option `care_behavior_timeline`，并把 `careBehaviorTimeline` sidecar 与整包 `questionPackage` / `uiHints` 一起提交给 `/diagnosis/answer`。

代码来源：`src/pages/diagnose/question-package.vue`；`src/pages/diagnose/question-package/question-flow.js`；`src/utils/care-behavior-timeline/logic.js`；`src/vue-query/diagnose/mutations/shared.js`。

## 6. 前端 payload

`buildQuestionAnswerPayload` 会从 question stack 构造 `answers`，包含 question key、option key、option value 与 answer text 等。题包模式由页面层传入整包 stack，并指定 `requestMode: answer_submit`。

代码来源：`src/utils/diagnose-question-answer-payload.js`；`src/pages/diagnose/question-package/question-flow.js`。

## 7. 必须暴露给前端的边界

前端可以按题包展示并提交固定题包全部题目；后端 answer endpoint 仍会做 question ownership 和 option mapping 校验。有效 `yellow_leaf` package 的包内问题来自 `questions`，后端通过 `runtimeSnapshot.questionPackageSnapshot.packageQuestions` 判定 allowed questions；`wilting_droop` 同样按 5 题 package 元数据和 snapshot 处理。固定题包的题数与归属不得被非题包路径约束。

黄叶 package 的结果展示必须以 route visible outcome 为准。过浇行为、施浓肥 / 近期换盆、直晒 / 光照突然增强三类强阳性完成整包提交后，应分别展示 `overwatering_root_pressure`、`fertilizer_repot_stress`、`sunburn`，不得展示为 uncertain。

枯萎/发蔫 package 的结果展示必须使用“建议行动清单”，并从 `visibleOutcomes`、`blockedActionExplanations`、`highRiskWarning`、`observationPeriod` 组织页面。前端不得把该结果显示为“最可能原因”，也不得引入排名、分数、概率或主因顺序。

## 8. 养护时间线环境上下文取数模式

- 前端在问诊场景请求 `weather-http/weather/environment-context` 时，带上 `mode: 'diagnosis'`，触发后端返回仅时光机历史窗口。
- `cloudfunctions/weather-http` 对 `mode='diagnosis'` 的 `environment-context` 请求，会对天气窗口进行裁剪，保留 `historicalDays`（兼容 `historical_days`）并将 `forecastDays/forecast_days` 计数归零，不再返回 `forecast` 与 `currentWeather` 字段。
- 构建时间线温湿度显示仍通过 `buildWeatherByDateFromEnvironmentWeatherWindow` 统一读取日期映射；诊断场景因此默认只使用历史窗口中的天气记录。

代码来源：`cloudfunctions/weather-http/app.js`、`src/api/weather.js`、`src/vue-query/weather/queries/environment-weather.js`、`src/pages/diagnose/question-package/question-flow.js`、`src/components/DiagnosePopup.vue`。

## 9. final 结果读取


最终输出必须以 route visible outcome 与 result formatter / result read service 的公开口径为准。旧的 primary/secondary 字段只能作为兼容输入被重构，不是新的事实出口。

## 10. 前端不得做的事

- 不得根据题包问题数组是否为空自行判定最终诊断已可展示。
- 不得根据完成题数绕过后端 stop/output 资格。
- 不得把黄叶 package 当成所有模式默认题包协议。
- 不得把 `wilting_droop` 的多 outcome 行动清单改写成“最可能原因”或主因排序。
- 不得忽略 `questionPackage` / `uiHints`，否则会把固定题包降级成 1 题。
- 不得把非 package 的单题 queue-anchor 外推成 package 题数权威。
