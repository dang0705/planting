## 微信开发者工具 MCP 真实连接与子代理协作记要（更新）

### 连接背景
- 目标：在真实微信开发者工具 MCP 上验证连接链路，采用端上 JSON-RPC 方式进行操作验证。
- 执行上下文：qa_reviewer 子代理任务流程中出现环境差异。

### 实际遇到的坑
- 首次尝试使用 `python` 命令执行连接脚本时失败（环境未提供 `python` 二进制）。
- 失败后改用 `python3` 继续执行，确认脚本能在当前环境运行，避免因为解释器别名导致的误报。
- 遇到的首要风险并非 MCP 本体不可达，而是执行环境层面的命令兼容问题（解释器入口）。
- 另一个可观测问题是端上点击路径误选，导致先进入错误模式（“枯萎/发蔫”路径），不是连接未建立。

### 最终解决方式（可复现）
- 统一使用 `python3`，不要再使用 `python`（除非明确存在并测试通过）。
- 使用 `wechat_devtools_mcp v0.9.8` 的真实 MCP 调用链路做验证：
  - `wechat_ide/status`：确认 MCP、CLI、Node、项目路径与 appid 正常；
  - `wechat_ide/is_login`：确认已登录态；
  - 自动化 `wechat_automator` 进入可交互状态（端口 `9420`，TCP/WS 已就绪）；
  - 按端上元素重新点击“黄叶模式”，避免误点错误入口；
  - 进入 `pages/diagnose/question-package` 页面并确认 `draftKey` 与问题路径。
- 结论：环境在解释器修正后恢复真实连接，关键路径在 250ms 内可见页面可观测切换。

### 子代理（qa_reviewer）配置与使用说明
- 角色：`qa_reviewer`
- 任务边界：仅做 QA 验证（unit/smoke/e2e/WeChat MCP/端上验证），不做代码评审。
- 启动参数要求：
  - `agent_type=qa_reviewer`
  - `fork_context=false`（对应 `fork_turns=none`，不带 full-history）
- 成功案例关键点：
  - 使用最小上下文任务描述，避免无关信息；
  - 指令聚焦“真实连接”与“原始错误返回”，不做替代/猜测回复。

### 经验结论
- 本次真实失败点优先级：连接链路 > 解释器环境 > 用户路径选择；实际最早触发阻断的是环境命令不可用，非 MCP 服务不可用。
- 规范化后续操作建议：
  - 固化脚本入口为 `python3`；
  - 连接探测先做 `status/is_login` 基础体检，再做 automator/navigate 的端上动作；
  - 子代理指令里固定要求输出原始结果与错误码/错误正文，便于后续证据归档。
