# 从设计产物写独立 Expected

行为义务以 `SKILL.md` 为准。期望值独立性见 [test-integrity.md](test-integrity.md) §2；改产品仍走 [product-safety.md](product-safety.md)。  
**何时读：** **实际使用**设计稿 / 原型作为外部真相源，且需要判硬锁 / 样例 / 待确认时读；仅仓库存在设计稿、或用户没有把设计用于本轮 Expected，不触发。父规则：[truth-sources.md](truth-sources.md)。  
本文件只写**抽象方法**。禁止写入某一仓库的业务名、页面名、文案样例或路由键。宿主如何拉取设计节点，服从该仓库自己的设计取数规则；本 skill 不绑定某一设计工具。

## 1. 设计是 Expected 来源之一，不是实现说明书

独立 Expected 可来自：外部契约、规格、手算 fixture、**经核对的设计可见结果**。  
设计 MCP / 导出物是**事实输入**；禁止用模型习惯补布局、补文案、补交互，再冒充设计合同。

禁止：

- 把设计参考代码或导出组件树当成可提交实现，再反推 Expected
- 用 SUT / mapper / builder 生成 expected 去「对齐」设计
- 设计未写明的接口字段、鉴权、错误码——不得靠「猜设计」发明

## 2. 先分辨：结构功能 vs 内容占位

设计帧上并非每条可见字都是产品合同。落 Expected 前必须给每条候选打档（可写在真实性表 Expected 来源旁）。

| 档 | 含义 | 默认可锁什么 |
| :--- | :--- | :--- |
| **硬锁（structure / behavior）** | 跨帧或同帧内**重复出现**的布局槽位、控件角色、状态机、用户动作 → 下游结果 | 侧栏/主区分工、单选/多选语义、空态与 loading 门闸、禁用不得副作用、半截受控回流、分区「标题 + 可选主视觉 + 可选子项网格」一类**模式** |
| **样例内容（content sample）** | 某一帧上的运营文案、条目名、营销 overlay、演示用列表项；可随 CMS / 活动 / 数据源替换 | 仅证明「给定该形 fixture 时 UI 按槽位渲染」；**不得**未经确认升成全站死文案合同 |
| **待确认（unconfirmed）** | 单帧无法证明的 IA 顺序、固定条目数、平台壳是否由本页实现、图层名与画面冲突项 | 标缺口或问清；禁止用待确认项逼产品改接线 |

### 2.1 升为硬锁的启发式（须同时尽量满足）

1. **重复结构 > 单次文案**：同一模式在多个分区 / 状态重复，比只出现一次的营销字更硬。  
2. **交互结果 > 展示装饰**：点选、切换、确认/取消、导航、mutate 是否发生，优先于像素级装饰。  
3. **可见状态 > 元数据噪音**：以渲染可见的选中态 / 文案为准；图层占位名、hidden 节点、画板路径名与画面不一致时，**降级**，不以路径名推断路由或业务。  
4. **工具事实 > 模型脑补**：尺寸、文案、状态以取数结果为准；取不到则 unresolved，不补全。

### 2.2 典型降级信号（默认不当硬锁）

- 仅出现在单帧、明显可替换的列表项 / 标题文案  
- 图层名为序号、假词、与可见文案不符  
- `hidden` / 未呈现节点、重复壳实例  
- 画板或 frame 命名与当前选中态、主文案冲突  
- 平台导航壳（顶栏 / 底栏等）：若仓库规定由 Layout 承担，矩阵 Expected 钉**页面主内容职责**，壳文案最多作全页态引用，不在内容页测里穷举壳实现

## 3. 分层怎么用设计 Expected

| 层 | 设计硬锁 | 设计样例内容 |
| :--- | :--- | :--- |
| **L1** | 纯函数 / mapper 的槽位规则（有图才渲染、无 id 不展示某槽等） | 一般不锁运营文案 |
| **L2** | 用户可观察的结构与交互（选中切换、点击下游、空/忙/禁用） | 可用**设计形 fixture** 证明渲染契约；fixture 须标明 content sample |
| **L3** | 契约字段与真实响应形状 | 真实环境内容以 live / 已批准制品为准；**禁止**把单帧设计文案冒充外部协议 Happy |

同一业务结果禁止在 L2 与 L3 用同一套死文案各穷举一遍：L2 锁模式与接线，L3 锁真实数据契约。

## 4. 从设计到用例的步骤

1. **取数**：按仓库设计取数规则拿到可见结构、文案、状态；记录 unresolved。  
2. **分档**：每条候选 → 硬锁 / 样例 / 待确认。  
3. **映射 §2.1**：硬锁进适用 U/C/I；样例只支撑 Happy 展示或标明 N/A 原因；待确认不落硬断言。  
4. **写独立 Expected**：可审计的用户结果（显隐、顺序模式、动作 → 下游），来源写「设计硬锁」或「设计样例 fixture」。  
5. **对现状**：硬锁 Expected 绿 = 产品已满足该设计合同（仍须突变检查，且须写明来源）。硬锁与产品冲突 = 表 1 的 A → 确认卡 + `product-safety.md` 闸门 2（Classic 或 Fast Path）完成 RED/GREEN 证明。禁止改 Expected 吞 A。仅钉「实现碰巧长什么样」且不引用设计分档 → characterization，不能声称按设计验收。  
6. **禁止**：用样例内容或待确认项申请改产品；为像素/% 改接线。

## 5. 与钉现状的关系

- 不引用设计分档、只复述实现 → characterization，不是 TDD。
- 硬锁与当前产品冲突 → 必须能证明错误实现会 RED；可 Classic 先红，也可按 §0 Fast Path 补反事实 RED。这是 TDD 入口，不是违反冻结。
- 执行反写仍用于证明断言硬度；≠ 用样例/待确认逼改产品。

## 6. 交付时 Expected 来源怎么写

真实性表 `Expected` 列须能看出档位，例如：

- `设计硬锁：侧栏单选切换主区，重选已选项不得导航`  
- `设计样例 fixture：给定 N 个分区标题时按序渲染（非 CMS 死合同）`  
- `待确认：条目固定数量 — 未落断言`

缺分档、把样例写成全站文案合同、或待确认已改产品 = **未完成 / 违规**。
