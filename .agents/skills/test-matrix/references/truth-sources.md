# 外部真相源与独立 Expected

行为义务以 `SKILL.md` 为准，尤其 §0。本文件展开「Expected 从哪来」。  
**何时读：** 当 Expected 不能由当前已给的单一明确来源直接写出，或需要主动采源、处理多源/冲突、分档、characterization、L3 契约时读。需求/DTO/规格已明确给出可审计 Expected 时，主文足够，不为重复确认预读本文件。  
本文件只写抽象方法。禁止写入某一仓库的业务名、页面名、路由键或具体文案样例。

设计帧分档细则见 [design-expected.md](design-expected.md)。期望值不得由 SUT 生成见 [test-integrity.md](test-integrity.md) §2。

## 1. 什么才叫独立 Expected

独立 Expected 是**可审计的「应当如何」**，即使与测试体同轮生成，也必须能脱离当前实现单独写出来，且**不依赖当前实现碰巧输出什么**。

一条合格 Expected 必须同时满足：

1. **有真相源**：能指出外部来源（下表一类或多类），或写明该维是 **common scene**（§2.1 固定场景，不依赖本对象源码发明）。
2. **可观察**：用户或契约消费者能核对的结果（字段、导航、payload、显隐、禁止的副作用），不是「某行代码变了」。
3. **手写或来自制品**：禁止 `expected = sut(x)`、禁止用同一 mapper / builder 生成两边。
4. **分档**：硬锁 / 样例 / 待确认。待确认不得落硬断言，更不得逼改产品。

源码、实现注释、现行 UI「看起来像」**不是**真相源。可读源码以识别 SUT 职责与 Real path，但 Expected 仍须从真相源或 common scene 写出。

## 2. 外部真相源（须主动采集）

按对象职责主动采集，**不得**等用户点名某份设计/DTO 才去看；可与测试侦察同轮完成。缺源 → 标缺口或待确认，禁止脑补合同。

| 源 | 锁什么 | 硬规则 |
| :--- | :--- | :--- |
| **DTO / 接口文档 / 已批准响应制品 / live 形状** | 字段名、类型、层级、必填/可选、错误码 | L3 Happy 禁止臆造字段。DTO 必须与文档或真实响应对齐才算合同；过时或「为前端改过形」的 DTO 不得当真相。制品可追溯 ≠ provider 已验证 |
| **设计稿 / 原型（经分档）** | 布局槽位、控件角色、状态机、动作 → 下游 | 只锁硬锁。样例内容只作 fixture。步骤见 [design-expected.md](design-expected.md) |
| **需求 / 规格 / 验收标准** | 业务规则、步骤、禁止项 | 未写明的接口形状不得靠猜需求发明 |
| **已批准跨会话 fact**（可选） | 稳定外部合同、跨边界规则、可移植根因、架构分层、高爆破环境约束 | **仅当仓库提供记忆插件 / 跨会话知识库时**才采。无插件 → 跳过本行，不臆造 fact。有插件时也**仅允许形状**的 fact；禁止过程笔记、未决猜测、表面展示细节、已有权威文件的复读。与现行文档/DTO/live 冲突时，以可核对的契约与响应为准，fact 降级待确认 |

冲突时的优先序（能核对的更硬）：**live / 已批准响应制品 ≈ 接口文档 ≈ 对齐后的 DTO** → **需求规格硬锁** → **设计硬锁** → **允许形状的 fact**。  
展示槽位以设计硬锁为准；数据形状以契约/live 为准。禁止用设计文案冒充 API 字段。

## 3. Common scene（与真相源正交）

[jargons.md](jargons.md) 的 U1–U7 / C1–C7 / I1–I5 是**固定场景目录**，不是从源码扫出来的 miss 行。

- 真相源回答「正确结果是什么」。
- Common scene 回答「哪些风险维必须有**独立**用例」（空缺、边界、禁用不得副作用、半截受控、写中断无半成品等）。
- 适用 → 至少 1 条独立 case，Expected 仍须独立（场景提供「测哪类错」，不提供「从 SUT 抄答案」）。
- 不适用 → 覆盖表 `N/A` + 一句原因。禁止为凑维编造与职责无关的 Edge。
- **列表 mapper 审查闸：** 适用 U1 时，覆盖表若只有「字段 null / 数组缺失」而无「**元素洞**（`[null, valid]`）」→ 维缺口，不得宣称 U1 已写完。样例见 [examples.md](examples.md)「数组元素洞」。

两者缺一都不算本 skill 的 TDD：只有合同 Happy、没有适用 Reverse/Edge = 维缺口；只有 common scene、Expected 从实现抄 = 自己测自己。

## 4. TDD 约束与执行路径

必须满足的不是固定动作顺序，而是以下证据：

1. **Expected 先独立确定**：DTO/文档/设计/需求；若仓库有记忆插件再采允许形状的跨会话 fact；记下 unresolved。硬锁条目 + 适用 common scene 在把当前实现当答案之前固定。
2. **测试不镜像实现**：断言手写；fixture 形状跟 DTO/设计槽位，不跟 mapper 输出互推。
3. **RED/GREEN 可审计**：代理自行选择执行路径。
   - **Classic**：先在当前产品上得到 RED；硬锁 Expected 红 = 表 1 的 A；确认卡后改该条产品至 GREEN。
   - **Fast Path**：来源与范围清楚时可省略显式 Plan、逐 case RED/GREEN 与额外 Refactor 阶段，一次完成测试/实现；交付前须用受控回退或代表性 Mutation 让目标 Expected RED，再完整恢复并 GREEN。反事实 RED 不成立 → 不得宣称完成，产品改动须回滚或测试须补强。
4. **绿仍要证明测试有牙齿**：GREEN 只说明现状满足 Expected；仍须按 [test-integrity.md](test-integrity.md) 做适用的 Mutation / 执行反写。
5. **无足够真相源**：只许标明 **characterization**（钉现状、防回潮），交付不得写成 TDD / 按合同验收；并列出缺哪类源。

结构第一次已合理时无需为了仪式再做 Refactor；需要重构时只要不改变 Expected 与 Scope，可与实现同轮完成并由同一套回归证据保护。禁止：先读实现写「应该如此」再去文档里找一句开脱；禁止为水位用源码启发堆 Happy。

## 5. 分层怎么用真相源

| 层 | 主真相源 | Common scene |
| :--- | :--- | :--- |
| **L1** | DTO↔域模型字段合同、规格谓词、手算 | U1–U7 适用维 |
| **L2** | 设计硬锁 + 需求交互；fixture 可标注样例 | C1–C7 适用维 |
| **L3** | live / 制品 / 接口文档；Edge 用构造风险数据打在真实经过的 mapper/编排上 | I1–I5 适用维 |

禁止同一规则在多层用同一套死文案各穷举一遍。

## 6. 交付

真实性表 `Expected` 列必须能看出：**源的种类 + 档位 + 一句可核对结果**。例如：

- `DTO/接口：缺 id 不得组进提交 payload`
- `设计硬锁：已选项再点不得二次提交`
- `需求：写请求进行中不得再 mutate`
- `记忆插件 fact（允许形状，仓库有插件时）：某跨页状态不得进全局 store`（须仍能指向可核对规则）
- `common scene C3：禁用点击不得触发下游`
- `characterization（缺接口文档）：仅钉现行空态文案 — 非 TDD`

缺来源、来源是 SUT、或把 characterization 写成合同验收 = **未完成**。
